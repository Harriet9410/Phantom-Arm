# records/ —— 实验记录

这里登记机械臂项目的**测试与验证记录**。

## 记录起点

**从 2026-09-21 02:00 起。**

此前的记录已全部清空，不再追溯。只登记这个时间点之后的测试。

## 为什么要有这个文件夹

三件事需要一个固定的地方存：

1. **这次的结论是什么** —— 通过了还是没通过，卡在哪
2. **用的是哪个版本的代码** —— 光有结论没用，得能对上代码版本
3. **改动的来龙去脉** —— 从哪个版本改到哪个版本，为什么改

注意这里只放**结论性文本**。原始数据（RGB-D、事件流、视频、模型权重）体积太大，留在服务器上或单独导出，不进这里。

---

## 目录怎么摆

一次测试一个目录，按时间命名：

```
records/
├── README.md
├── 20260921-1430_官方五条示例/
│   ├── run.json          启动参数与代码版本
│   ├── result.json       执行结果
│   └── notes.md          结论、发现的问题、下一步
└── 20260922-0915_第24轮复现/
    └── ...
```

命名规则：`YYYYMMDD-HHMM_简要说明`

- 时间用**开始测试的时刻**
- 说明写短一点，能一眼认出是哪次就行（比如"官方五条示例"、"第24轮复现"、"停止专项"）
- 同一天多次测试就靠时间区分

如果一次测试产生很多文件（探针脚本、补丁、诊断报告），全都放进对应的那一个目录里，不要散落在 records/ 根下。

---

## 每次要放什么

**必须有：**

| 文件 | 内容 | 来源 |
| --- | --- | --- |
| `run.json` | 启动参数、代码版本哈希、开始时间 | 服务器上的 `*_job.json` |
| `result.json` | 结果状态、验证数量、耗时 | 服务器上的 `summary.json` 或 `*_status.txt` |
| `notes.md` | 人写的结论 | 手工补 |

**按需放：**

- 失败归因（`*_diagnosis.txt`）
- 补丁记录（`patch_*.diff`）—— 代码改了就要留，带哈希的那种
- 独立预期答案（`*_oracle.json`）
- 审计结论（如 `COMPLETION_AUDIT.json`）
- 一次性探针脚本（`probe_*.py`）

**不要放：**

- RGB-D 记录（`*.npz`、`*.jpg`）
- 完整事件流（`events.jsonl`）
- 视频、截图（`*.mp4`、`*.png`）
- 模型权重（`*.pt`、`*.safetensors`）
- 代码副本（代码在 `arm/`，版本用 git 管，不要复制到这里）

---

## 和 arm/ 怎么配合

`arm/` 是代码，`records/` 是测试记录，两者靠**版本哈希**对上。

`run.json` 里的 `source_sha256` 必须和当时 `arm/` 的代码版本一致。这样以后回看某次失败，能准确回到那版代码。

代码改了之后，旧记录不要改，另起一个新目录登记新测试。

---

## 怎么从服务器同步

测试在云实例上跑，跑完把**小文本**拷回来：

1. 在服务器上按测试批次打包（只挑 `*_job.json`、`*_status.txt`、`summary.json`、`*_diagnosis.txt`、`patch_*.diff` 这类）
2. 传到本地，解压进 `records/<对应目录>/`
3. 补一个 `notes.md` 写结论

**注意 `/root/gpufree-data/` 下的内容在释放实例、制作镜像时不保存。** 重要记录要及时拷出来，别等实例释放了才发现没了。

## 几条规矩

1. **失败了也要登记。** 失败比成功更值得记，换种子重跑不能算数，失败要留在分母里。
2. **代码改了要留补丁。** 光记结论不记改动，回头对不上。
3. **结论写清楚依据。** 别只写"通过了"，要写清楚是几件通过、几件待核验、耗时多少。
4. **"待核验"不是成功。** 比如任务 5 那种情况，动作做完了但没拍到落点证据，要如实记录。
