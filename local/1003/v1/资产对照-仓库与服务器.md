## 四、"仓库够不够？"——分两个目的回答

### 4.1 目的 A：**学习/拆解项目** → **基本够（约 85%）**

**够的部分**：
- ✅ **我们写的全部代码**（arm/ 185 文件，含 37 个运行模块）——算法主战场（九格选块、身份跟踪、账本校验、核验）都在
- ✅ **官方源码与场景**（source_code/ 234MB）——仿真、机器人、场景资产齐全
- ✅ **架构文档**：`docs/源码说明书.md`（源码导读）、`arm/docs/运行入口说明.md`（运行链）、`视觉参与控制逻辑核对.md`（视觉与控制边界）
- ✅ **分阶段学习笔记**：`notes/阶段1~5`（大模型输出契约 → 深度取值 → 抓取重试 → TRRT 参数 → 接近偏移），是理解仿真侧设计的现成教材
- ✅ **演进史**：`progress/CHANGELOG-dev.md`

**缺的部分（影响深度但不阻塞）**：
1. **"为什么这么改"的推理过程**——在 `local/1002/`、`local/1003/`（阶段0~17 全部记录、方案、操作卡、使用手册），**被 .gitignore 排除**。读代码能看到"是什么"，看不到"为什么"（例如为什么移除类别稳定门、为什么加布局先验）
2. **模型内部**——8.5GB 模型与建模代码不在仓库；但**调用契约**（我们怎么用它）在 `nine_classify.py` 里，读它就能理解算法接口
3. **模型训练资料**——`local/feishu/`（九格多模态大模型4B量化与训练使用手册、量化和训练）也不入库

> 结论：**只读仓库能学懂 85%**；加上 `local/` 的文档才完整。

### 4.2 目的 B：**备份进度** → **不够（约 60%）**

**已在仓库**：代码 + 场景 + 案例 + 标定 + 清单（本机与 gitee 双份）✅

**没备份的关键项**：

| 缺口 | 体量 | 丢了的后果 | 补齐方案 |
| --- | --- | --- | --- |
| **① 模型（基座 8.5GB + LoRA 适配器 382MB）+ 那行补丁** | 8.9 GB | 无法运行（基座不可再生；适配器需重训） | 打 tar 快照到持久位置；**补丁 diff 已入库**；**适配器副本在 `9.29存档.zip` 内** |
| **② `local/` 全部工作记录** | 251 MB | 推理过程、已知限制、操作卡、交接文档全丢 | 择要入库（或取消 ignore 后选择性提交 md/txt/pdf） |
| ③ 实例状态 | 小 | 需重跑 `init` | 记录 INSTANCE_ID 与 instance.env 模板入库 |
| ④ Python 环境清单 | 小 | 重建环境靠猜 | `pip freeze` 两个环境导出入库 |
| ⑤ 运行数据 | 36 GB | 证据丢失（一般可弃） | 只留关键回合的 summary/证据 |

**建议的最小补齐动作（约 10 分钟，不改代码）**：
```bash
# 1) 模型补丁入库（唯一无记录的代码改动，先保护）
ssh 到实例 → diff -u modeling_fm9gv.py.bak_prepatch modeling_fm9gv.py > arm/docs/模型补丁-modeling_fm9gv.diff
# 2) 环境清单入库
/opt/conda/envs/inference/bin/pip freeze > arm/docs/requirements-inference.txt
/opt/conda/envs/yolov8/bin/pip freeze   > arm/docs/requirements-yolov8.txt
# 3) local 文档择要入库（新开一个 docs 子目录，不取消 local/ 忽略）
mkdir -p arm/docs/工作记录 && 复制 1002/1003 的 md + feishu 手册
# 4) 模型快照（放持久位置，不入 git）
tar -czf /root/gpufree-data/snapshots/FM9G4B-V-$(date +%m%d).tar.gz -C /root/inference FM9G4B-V
```

## 七、9/29 训练改变了"大模型本体"吗？——**没有**

**结论：9/29 的三轮训练全程是 QLoRA（低秩适配器训练），没有动基座权重一分一毫。模型本体（8.5GB）仍是 2026-03-09 的原始文件，训练只是**在旁边产出一个 382MB 的 LoRA 适配器**，运行时用 `PeftModel` 挂到基座上。**

### 7.1 三条独立证据链

| # | 证据 | 说明 |
| --- | --- | --- |
| ① 文件时间 | 基座 `pytorch_model.bin`（9.03GB）**mtime = 2026-03-09**，训练日（9/29）之后从未被写过 | 若训练改写基座，mtime 必然变成 9/29 |

| ③ 加载代码 | `tcei_stack/nine_node.py:73-91`：先 `from_pretrained(基座)`，再 `PeftModel.from_pretrained(base, '/root/sft_v2/outputs/qlora_crop/step_27000')` **在运行时把适配器挂上去** | 基座文件被读取而非写入；适配器是独立目录 |

### 7.2 三层资产的实际关系

```
基座 FM9G4B-V (9.03GB, 2026-03-09, 未变)   ← 8.5GB 目录
   ＋ 补丁 modeling_fm9gv.py（3 行，2026-09-25，修 input_ids 报错）
   ＝ 可运行的"部署模型"
   ＋ LoRA 适配器 qlora_crop/step_27000 (382MB, 9/29 训练产出)
   ＝ 九格分类/落地框推理时实际生效的完整权重
```

- **补丁**改的是**建模代码**（Python），不是权重——且**已入库**（`arm/docs/模型与环境恢复/`）
- **适配器**才是 9/29 训练的产物，**只有 382MB**（vs 基座 9GB），因为 LoRA 只训低秩增量
- 训练**从未**产生新的基座文件；`/root/sft_v2/outputs/` 下三轮产物全是 `adapter_model.safetensors`（191MB / 382MB / 382MB）

### 7.3 对"备份"的含义

- 需要备份的**不是**"训练后的新基座"（不存在），而是 **①基座（8.5GB，不可再生）+ ②适配器（382MB，可重训但成本高）**
