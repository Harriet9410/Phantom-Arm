# 根因分析：类别标签"错位"——为什么每个场景、每条后段指令都会失败

> 分析时间：2026-10-04（晚）
> **状态：✅ 已修复并部署（2026-10-04 晚，dev_v7_t1_36）** —— 见第八节
> 触发：`manual_041610` 第 4 条「抓取手雷」被拒 `vision/model category disagreement`（前 3 条全部成功）
> 结论：**九格的类别是按"当前帧候选的排序下标"挂载的；候选集合每抓走一件就变、顺序还会翻转、扫描是异步的 —— 于是旧编号的类别被贴到了新编号的物体上。** 这是"后段指令几乎必败"的结构性根源。

---

## 一、决定性证据（四条）

### 证据 1：发布的标签里出现了"已经不存在的类别"
手雷任务发起时（t≈1791101949），候选只有 2 个：

| 候选 | 视觉标签 | 实际是什么 |
| --- | --- | --- |
| id=1 | Smokegrenade | 烟B（中心）——标签**对** |
| id=2 | **Magazine** | **手雷**（右上方）——标签**错**，而且**场景里早没有弹夹了**（第 2 条就抓走了） |

### 证据 2：扫描自己的答案是对的，且从未说过 Magazine
同一次扫描的全图编号查询（`nine.log`）：

```
t=1791101949  {"1":"Smokegrenade","2":"Grenade"}     ← 扫描说 2 号是手雷 ✓
```
**而 `Magazine` 这个词在本轮全部 197 条分类答案里，最后一次出现是 t=1791101637**——比这次任务早了 **312 秒（5 分钟）**，当时弹夹还在场上。

→ **发布的 `Magazine` 标签根本不是这次扫描产出的，是 5 分钟前的旧标签被贴到了新候选上。**

### 证据 3：扫描的编号顺序在不同帧之间**翻转**
历次全图编号查询（同一场景、同一批物体）：

```
t=1791101737  {"1":"Smokegrenade","2":"Grenade"}
t=1791101860  {"1":"Grenade","2":"Smokegrenade"}   ← 顺序反了！
```
同一件物体，上一帧是"1"，下一帧就是"2"。而类别缓存是**按编号（下标）存的**。

### 证据 4：模型其实看对了图
模型三次都答 `{"class":"Grenade","side":"right","ids":["1"]}` —— 它想抓手雷（场上确实有），但它的"1 号"与标签的"1 号"不是同一件物体。**视觉标签与物体错位，模型和守卫各说各话。**

## 二、机制（代码层面）

`tcei_stack/nine_classify.py`：

```python
# 扫描（后台线程）：类别按"提案序号"存
self._cache = {'at': time.monotonic(), 'assign': dict(self._stable_assign)}   # assign[下标] = 类名
...
# 发布（每帧）：用缓存按"当前帧下标"贴类别
for index, cls in assign.items():
    row = {'class': cls, ...}                    # ← 下标 ↔ 类名，没有物体级匹配
```
而提案顺序来自 `source_components` 的输出（**按 bbox 的 x 排序**）：

```python
boxes = sorted(boxes, key=lambda b: b['bbox'][0])     # 每帧重排
```

于是三重错位叠加：

1. **物体被移走** → 候选数 5→4→3→2 → 下标含义整体偏移
2. **剩下物体的左右顺序变化**（手臂进入视野、物体被碰动）→ 下标在两件物体之间**翻转**
3. **扫描是每 60 秒一轮、发布是每帧** → 发布用的是上一轮扫描的编号

**再叠加我加的"标签完整门"**：它只要求"所有真实候选都有类别"——而那套**过期但齐全**的旧标签正好满足条件，门立刻放行，计划就用 5 分钟前的标签去校验。

## 三、为什么"每个场景都会不行"（而不是偶发）

| 因素 | 数值 |
| --- | --- |
| 每场景物体数 / 抓取次数 | 5 件 / 5 条指令（4 次移走） |
| 每次移走都改变候选集合与顺序 | 4 次错位窗口 |
| 一次任务周期 | ~45–70 秒（抓取+放置+核验） |
| 扫描周期 | 60 秒 + 按需触发（异步，落地要 20–40 秒） |

→ 后段任务（第 2~5 条）几乎**总是**落在"集合已变、新扫描还没落地"的窗口里。所以：
- 第 1 条通常没事（场景没变过，启动扫描的编号是最新的）
- **第 2 条起开始随机出错**，越往后越容易（错误标签越陈旧）

这也解释了历史现象：弹夹被标 unknown / 手电筒被标 Torch / 手雷被标 Magazine / 双 Torch —— **都是同一族"标签跟着编号跑、不跟着物体跑"**。

## 四、为什么之前的修复都只把失败点往后推

| 修复 | 治的是什么 | 为何不够 |
| --- | --- | --- |
| 超时 10s→25s | 扫描丢票 | 减少误标，不解决错位 |
| 标签完整门 | 计划发起时标签还空 | 门只查"有没有标签"，**不查标签是不是这件物体的** |
| 账本未知类别污染 | 账本把 unknown 当既成事实 | 同理，是下游消费者 |
| 碎片豁免 | 极值指令被碎片挡住 | 同理 |
| 持物减速 | 弹夹中途掉落 | 另一类问题（已单独解决） |

**共同点：全都在下游打补丁，没碰"类别↔物体"的绑定。** 这是这次必须修的根。

---

## 五、建议的修法（**未实施，等你决定**）

### 主修（推荐）：把类别绑到物体上，而不是绑到下标上
`nine_classify.py`：
1. **扫描时**：`_scan_worker` 除了存类名，同时存**该物体的几何**（扫描那一帧的 bbox / 中心像素）
2. **发布时**：对当前帧每个提案，按**几何匹配**去找扫描时的对应物体（bbox 重叠 / 中心距 设阈值），匹配到才贴类名；**匹配不到就发布 `unknown`**
3. **失效**：集合或几何变化过大时自然产生 `unknown` → 触发新一轮扫描（现有 `pending_scan` 机制已具备）

效果：类别跟随物体，不再随下标漂移；新出现的提案不会被贴上旧标签。

### 佐修（便宜、可先做）：缓存失效
发布前比对"当前提案几何"与"缓存建立时的几何"；变化超过阈值 → **整批作废**（全发布 unknown）→ 由标签门等新扫描。代价：每次抓取后要多等 20–40 秒（因为要等新扫描），但**标签必然是最新的那一批**。

### 可选：把"下标"换成稳定身份
更彻底的做法是让九格的分类结果经由 `CandidateTracker` 的 **stable_id** 绑定（感知侧已有身份跟踪）。改动面更大，作为后续。

## 七、一句话

**模型看图是对的、扫描单次也是对的，坏在"类别按候选排序下标挂载 + 集合每抓一件就变 + 扫描异步"——旧编号的标签被贴到新编号的物体上，越到后段越陈旧。修法是把类别绑到物体（几何匹配）而不是绑到下标，并让缓存随集合变化失效。**

## 八、✅ 修复实施（2026-10-04 晚，dev_v7_t1_36）

**改的文件**：`tcei_stack/nine_classify.py`（冻结运行时；同步刷 `BUILD_MANIFEST.json` 与 `PACKAGE_MANIFEST.json`）

**改法（主修 = 几何绑定，佐修 = 缓存超龄作废）**

1. **新增几何匹配**：`_centre()` + `_associate(proposals, objects)`
   - 按**中心距 ≤ 20 像素**做**一对一**最近匹配（物体间距 ≥40 像素，不会串）
   - 记忆里的物体若再也匹配不上任何提案 → 自然淘汰；提案若匹配不上记忆 → 发 `unknown`
   - **类别永远不可能"迁移"到另一件物体上**
2. **类别记忆改为物体级**：`self._objects = [{bbox, pixel, class, pending}]`
   - 旧实现 `_stable_assign/_last_assign`（**下标键**）全部删除
   - 滞回规则不变（**连续两轮一致才改判**），但比对发生在**同一物体**之间，而不是"同一下标"之间
3. **发布路径重写**：`detect()` 里 `self._cache['assign'][index]` → `_associate(proposals, self._cache['objects'])`
4. **缓存超龄作废**：新增 `CACHE_MAX_AGE = 150s`（超龄整批作废，强制等新扫描）

**单测（用真实失败帧的几何，本地与服务器各跑一遍，结果一致）**

| 场景 | 输入 | 结果 |
| --- | --- | --- |
| ① 真实失败帧：弹夹已抓走，剩 烟B+手雷，旧缓存里含 Magazine | 提案=[烟B框, 手雷框] | **{0:Smokegrenade, 1:Grenade}**，Magazine 不再出现 ✓ |
| ② 候选顺序翻转（实测 t=1860 发生过） | 提案顺序颠倒 | {0:Grenade, 1:Smokegrenade} ✓（旧实现此处必错） |
| ③ 新出现/无匹配的物体 | 提案含一个陌生位置 | 只有匹配上的那件贴类名，其余 unknown ✓ |
| ④ 两件物体靠得很近 | 两个提案都在阈值内 | 一对一，只有一个拿到类名 ✓ |

**服务器校验**：`verify_package` PASS(152)、BUILD 自检 **0 失配**（`dev_v7_t1_36`）、三处改动源码逐条确认（几何绑定已生效 / 下标记忆已彻底移除 / 超龄门在场）

**预期效果**：第 2~5 条不再出现 `vision/model category disagreement`（标签与模型看到的一致）；移除的物体标签立刻消失；新遮挡/新出现物体先发 `unknown` → 由标签门等新扫描（不会再用陈旧标签校验计划）。

## 补充（10/4 深夜）：几何绑定第一版引入的回归，与最终修复（dev_v7_t1_37 / t1_38）

**第一版（t1_36）落地后，用户实测 `manual_041630`：0/5，比修前更差**，失败串全为 `vision/model category disagreement`，且**第一条就挂**。

**为什么"全部未知"会表现成 category disagreement**：`semantics.py:367` 的判定是
`candidate['class'] not in CLASSES or (category != 'Remaining' and candidate['class'] != category)` → 抛 `vision/model category disagreement`。
`unknown` **不在** `CLASSES` 里，所以"**全部候选 unknown**"与"**标签贴错物体**"是同一条报错——这正是第一版把标签清空后的表现。

**第一版的缺陷（我引入的）**：t1_36 把记忆写成"**本轮观测整体替换** `self._objects`"。而扫描是异步的、会被模型加载/超时打断：
- 一次**空扫描**（`assign={}`）→ `observed=[]` → **整批记忆被清空** → 所有候选变 `unknown` → 每条指令必被拒
- 实测证据：任务 1 的 5 个候选**全部 `unknown`**，而 `coverage_complete: true`、`obs_wait=14.4`；`nine.log` 里 57 条 `classify_answered`、**0 条扫描失败** —— 扫描"成功"了但答案为空，记忆就被抹掉
- 同时"已就绪"机制失效：重扫反而清掉旧标签，**越扫越未知**

**最终修复（dev_v7_t1_37，已部署）**

| # | 改动 | 作用 |
| --- | --- | --- |
| 1 | **记忆保留**：本轮未观测到的记忆条目保留 `RETAIN_SECONDS = 90s` | 空/残缺扫描不再清空类别 |
| 2 | **逐条年龄** `seen_at`（取代"整缓存过期"） | 只在物体真的消失 90s 后才淘汰 |
| 3 | **自适应重扫**：真实物体覆盖不足且缓存年龄 > `LABEL_RESCAN_AFTER = 10s` | 缺标签 10 秒内自动补扫，不再干等 60s 周期 |
| 4 | **碎片过滤** `_is_real_box`（bbox 面积 ≥ `REAL_BOX_MIN_AREA_PX = 500`） | 与 nine_node 标签门**同一阈值**，碎片不再拖住等待 |
| 5 | **扫描日志** `nine scan: classified %d/%d proposals, memory %d` | 现场可判读"扫描到底认了几件" |

**回归测试（本地 + 服务器各一遍，结论一致）**：空扫描 → **保留全部 3 条记忆** ✓；部分观测（只看到 2 件）→ 保留 3 条 ✓；超过 150s 未见的条目被忽略 ✓。
