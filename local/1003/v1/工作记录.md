## 10/4 续19 — 磁盘闸闭环：真因是"API 删除进回收站"，不是泄漏（可用 7.9 G → 35 G）✅

**现象链**：十场景批量 0 轮 → `scripts/run_round.py:33` 的 8 GiB 闸 → 数据盘可用只剩 **7.9 GiB**。

```
drwx------ .Trash-0            ← du -sh /root/gpufree-data/.[!.]* → 27G
```
`jupyter_server` 的 `FileContentsManager.delete_to_trash` **默认 True** —— 我的 DELETE 不是 `unlink`，而是把 52 个 `rgbd` 搬进了**该文件系统的回收站**（自动改名 `rgbd.8`…`rgbd.51`，共 55 个条目）。账目于是完全自洽：**可见 14.6 G + 回收站 27 G = 42 G = `df` 已用** ✓；且 `lsof +L1` 为 0、`findmnt` 无嵌套挂载 → **既没有泄漏进程，也没有遮蔽**。

**处置**：shell 里 `rm -rf /root/gpufree-data/.Trash-0` → **可用 7.9 G → 35 G（已用 15 G / 30%）** ✓ 8 GiB 闸通过。清空后保留完好：`episode/summary.json`、`scalars/events.jsonl` 全在，一周以内轮次与活动包未动。

**三条教训（已写进清单 §10.8，第 0 条最重要）**：
0. **经 Jupyter API 的删除是"软删除"→ 进 `.Trash-0`，不释放空间**；要真腾空间只能用 shell 的 `rm -rf`，或 API 删完再清空回收站。
1. DELETE 缺 `X-XSRFToken` 头 → **403**，原文 `'_xsrf' argument missing from POST`（易误读成"服务器禁止删除"）。
2. `?content=1` 的目录列表会返回**缓存旧值**（删完仍列出 4791 个文件）→ 验证必须用文件级 `?content=0` 探测（200/404）。
