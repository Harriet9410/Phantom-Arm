### 2.2 对"比赛版"的直接含义（重要）

1. **模型资产必须单独做快照**——gitee 放不下（8.5GB）也不该放。建议：比赛前对 `/root/inference/FM9G4B-V` 打 tar 快照放在**另一个持久位置**，并把 `modeling_fm9gv.py` 的补丁 diff 以文本形式存入仓库（补丁很小，可入库）。
2. **克隆实例 ≠ 完整备份**：数据盘（`/root/gpufree-data`）官方文档说**不随镜像保存**，而模型/场景/环境都可能在系统盘（本次在 `/root` 下，随镜像走）。比赛前要逐项确认"哪些会随镜像、哪些不随"。
3. **换实例后的重建清单**：`robot.sh init`（生成 instance.env）→ 确认模型/场景/环境路径 → 冻结清单校验 → 起栈冒烟。

## 三、问题 2：fork 出来的会话可以用 skill 吗？——**可以**

- **可以**。Skill 是**按会话加载**的，fork 会话与普通会话在这一点上没有区别。本会话的可用 skill 列表里已包含你点名的两个（`grill-me`、`ponytail`），我可直接用 Skill 工具调用它们。
- 用法两种：①你像刚才那样输入 `$grill-me` / `$ponytail`（或 `/` 形式）触发；②直接说"用 grill-me 盘问我"我来调用。
- 提醒：fork 继承的是**上下文与工具环境**，不继承父会话"还没做完的动作"——父会话里未完成的工具任务（如后台进程）在 fork 里要用实例端现状重新确认。

**这两个 skill 用在哪最合适（我的建议）**：
- `grill-me`：在你**定稿比赛版设计**时用——它会连珠炮式追问设计里的含糊处（例如"被拒后比赛方会不会继续发下一条？""核验失败算不算完成？"），正好把比赛版最容易翻车的边界问清。
- `ponytail`：在**动手改代码前**用——它的立场是"能不改就不改、能删就删"，正好压住"为小问题引入大改动"的冲动（今天的布局先验就是"最小改动治根因"的样板）。

## 四、我心中的比赛版（供你设计时对照）

**一句话：一个自包含、可冒烟、可复现的"比赛包"，现场只需两条命令，五条指令全部走完且证据完整。**

### 4.1 形态目标

| 层面 | 目标 | 现状差距 |
| --- | --- | --- |
| **运行形态** | 默认场景 + 官方五条**逐条发**；单条 ≤60s、五条 ≤6 分钟（600s 预算内留 30% 余量） | 单条 42-60s ✅；五条总时长未掐表实测 ⚠️ |
| **成功率** | 五条**全部完成**（物理送达 + 核验确认） | 物理 5/5 ✅；核验间歇 ⚠️（唯一硬缺口） |
| **操作形态** | 现场两步：`start` 起栈 → 逐条 `run`（或比赛方接口下发）；**无需任何手工修复** | 手顺 OK；但"被拒/异常后怎么办"的现场预案未定稿 ⚠️ |
| **合规形态** | 零 YOLO 证据链随包可查（进程参数、面板标题、无权重加载） | ✅ 已具备 |
| **可复现形态** | 从 gitee + 模型快照 + init 三步重建整个实例 | 模型快照方案未做 ⚠️ |

### 4.2 我心中的"最终版"要做的五件事（优先级排序）

1. **核验稳定化**（唯一硬缺口）：按《剩余物品修复方案.md》附二方向修——用 `release_id/stable_id` 绑定区分"新放的"与"早先放的"同类物体；目标：连续 3 轮彩排 ≥ 4/5 条核验通过。
2. **比赛现场预案定稿**：每个可能故障（被拒/超时/核验未确认/进程死）对应一张"一句话卡片"，写进操作卡；演练一次"故障恢复"。
3. **包与资产冻结**：模型目录快照 + `modeling_fm9gv.py` 补丁 diff 入库 + `state/` 备份；`robot.sh doctor` 全绿作为"比赛包体检"标准。
4. **全真彩排**：默认场景完整跑 3 轮五条（掐表、录屏、逐条留证据），产出"比赛版验收记录"。
5. **代码通读**：把 4 个运行节点（sim 我们只读、controller/perception/nine 是主战场）的关键路径读通——重点：**我们的改动面 vs 官方原版**的边界清单（哪些是我们加的、为什么加、比赛时是否有副作用）。

### 4.3 明确不做的（止损）

- 不追随机布局泛化（30 案例）作为比赛主目标——比赛用默认场景；随机刷仅作训练参考
- 不为"剩余物品"的极端场景（多物体中途交付）继续加码——已可执行，核验问题一并修；超出不恋战
- 不改官方文件（`jaka_sim.py` 等已在实例上打的补丁保持原样，改动都留在我们的 4 层内）

## 五、双线工作法（"了解代码"与"做最终版"同时进行）

每个改动/保留点都走同一循环：**读代码（仓库）→ 在实例上核对（现状/行为）→ 决策（改/不改）→ 验证（实测）→ 记录（文档）**。

三条并行线：

| 线 | 内容 | 产出 |
| --- | --- | --- |
| A 资产线 | 模型/场景/环境/配置盘点与快照 | 实例资产清单 + 快照 + diff 入库 |
| B 代码线 | 四节点关键路径通读 + 我们的改动边界清单 | 改动地图（谁加的/为什么/风险） |
| C 比赛线 | 核验修复 + 现场预案 + 全真彩排 | 比赛版验收记录 |
