## 三、Q2：斜放（立姿/倾斜）——**没有验证过**

### 结论
- **识别侧**：九格**很可能"看得见"**斜放/立姿物体（代码把它保留为候选），但**从未在斜放场景上验证过出框率**。
- **抓取侧**：只有 **±10° 的有限回退**，且只在 **2 个历史案例**上成功过；**超过 ±10° 的斜放既无处理也无验证**。
- 而且 **官方 30 题库本身明确不测斜放**——所以"刷 30 题"也回答不了这个问题。

### 证据

**1）30 题库自己不测斜放**（全部 30 个文件同一行）
`arm/cases_official30_v2/official_random_01.json:351`
```
"original roll/pitch retained; not stacked/upright stress"
```

**2）识别侧：只出类别框 + 图像平面内长轴角，没有 3D 姿态**
- `arm/tcei_stack/nine_classify.py:9`：`"Rotation stays with the geometry stage."`（旋转交给几何阶段）
- `arm/tcei_stack/rotation_perception.py:118-131`：只算图像主轴 `theta`，近圆物体强制 `angle=0`
- `arm/tcei_stack/perception.py:240`：候选里只有 `angle_deg`（图像长轴），**没有 roll/pitch**
- `arm/tcei_stack/perception.py:245-247`：立姿/堆叠物体**仍保留为可见候选**，只是 `grasp_ready=False`
  ```python
  # Do not reuse the old 2.50 m height cut-off: standing/stacked
  # objects remain visible candidates with grasp_ready=False.
  ```
  → 即"看得见、判不可抓"，**不等于识别失败**

**3）抓取侧：只有 ±10° 回退**
- `arm/tcei_stack/core.py:83-84`：倾角**只接受 0 / +10 / -10**
  ```python
  if ... tilt_deg not in (0.,-10.,10.): raise ValueError('unsupported bounded grasp tilt')
  ```
- `arm/tcei_stack/controller.py:1089-1092`：竖直候选全部试尽后，才进入 tilt 家族
  ```python
  for tilt in (0.,10.,-10.): ...
  ```

**4）验证记录：只有 2 个案例，且是"有限倾斜"**
- `arm/validation/tilt23_old24_preview_observed.json`：只读预检，`vertical_valid: 0`，仅 `+10/yaw0` 与 `-10/yaw180` 通过全部 6 阶段，`motion_commands: []`（未动）
- `arm/validation/old_edge_tilt23_01_observed.json`：case 24「Magazine→left」、case 26「Torch→right」，`physical_complete: true`
- 服务器留档：`/root/gpufree-data/tcei_tilt23/old_edge_tilt23_01_random_24{,_round}`、`..._random_26{,_round}`

**5）参考：zy 组的"5/5 含立姿"是 YOLO**
那是 zy 重训 YOLO 的成绩（`ae/jaka/best.pt`），**不是九格**。九格的训练数据是 1200 张裁剪图，**没有针对斜放做专门增强或评测**。

### 缺口
| 维度 | 现状 |
| --- | --- |
| 斜放**识别**（出框/选对） | 未测（代码上应可见，但无数据） |
| 斜放**抓取** ≤10° | 已验 2 例成功 |
| 斜放**抓取** >10° | **无处理、无验证**（代码直接拒绝） |

### 建议
1. **先做一次斜放实测**（小成本）：用现有 case 24/26 的旧 tilt 场景，或手工把 1~2 件物体摆成明显倾斜，用**九格**跑一轮，记录：出框率 / 选对率 / 抓取成功率。
2. 若实测出框正常但抓取失败 → 问题在抓取侧（±10° 不够），可考虑放宽 tilt 集合或加姿态补偿；
   若出框本身就差 → 才需要考虑**给九格补斜放训练数据**（成本高，约 12 h）。
3. 把"斜放"单列一个测试场景集（不混进官方 30 题），避免混淆评分口径。

## 四、Q3：九格↔YOLO 切换——**你的设想正确，我建议做成启动参数**

> ✅ **状态（10/3 20:2x）：已实现**。默认 `nine`，加 `--detector yolo` 切 YOLO；改动落在 `harness/launch_stack.py` + `scripts/start.py`，`verify_package` PASS。**实现时发现并采纳的关键约束**：nine 节点是语义规划与证据来源，**两种模式都必须启动**（否则回合的 nine 证据链断裂、整轮失败）——所以"纯 yolo"= **检测器换 YOLO、规划仍由九格承担**，这也正好是干净的检测器 A/B。详见 `工作记录.md` 20:2x 条。**尚未部署到实例、未提交 git。**

### 现状：切换**必须改代码**（不方便）
链路：`bash robot.sh start <名>` → `scripts/start.py` → `harness/launch_stack.py`

- **开关被写死在** `arm/harness/launch_stack.py:55`：
  ```python
  ('perception',str(code),[config['yolo_py'],'-u',str(code/'perception.py'),
      '_show_gui:=false','_weights:='+config['weights'],
      '_yolo_enabled:=false','_detector:=nine']),
  ```
- 接收端 `arm/tcei_stack/perception.py:48-60`：读 `~yolo_enabled`（**默认 True**）与 `~detector`（**默认 'yolo'**）；
  `perception.py:177-184` 按 `detector_mode=='nine' or not yolo_enabled` 分流。
- **全仓库没有任何 CLI 参数或 `TCEI_*` 环境变量能改这两个值**——想跑纯 YOLO，只能改 `launch_stack.py` 第 55 行。
- 而且 `harness/launch_stack.py` **在 `PACKAGE_MANIFEST.json`（159 条）里**，改完还要重校验清单。
- 另外 `local/1001/zeroyolo_perc.sh` 只是"手工重启 perception 节点"的临时脚本（路径硬编码），**不是正式开关**。

> 附：`robot.sh` 只有 24 行，`start` 分支是 `exec /usr/bin/python3 scripts/start.py "$@"`——**参数是透传的**，所以加开关很自然。

### 推荐方案：加一个 `--detector` 启动参数（默认九格）

**改动三处（约 10 分钟），之后切换只改命令、不改代码：**

**① `arm/harness/launch_stack.py`**
```python
# 1) 新增参数（默认取环境变量 TCEI_DETECTOR，再默认 nine）
parser.add_argument('--detector', choices=('nine','yolo'),
                    default=os.environ.get('TCEI_DETECTOR','nine'))
# 2) 按 detector 拼 perception 参数（替换第 55 行的硬编码）
det = args.detector
perception_params = ['_yolo_enabled:=%s' % ('false' if det=='nine' else 'true'),
                     '_detector:=%s' % det]
# 3) yolo 模式不启 nine 节点（省 8.5G 模型加载与显存）
spec = [...] if det=='nine' else [三个节点，去掉 'nine']
# 4) launch.json 里记录本轮 detector（审计用）
```

**② `arm/scripts/start.py`**：加 `--detector` 并转发给 `launch_stack.py`（现在只有 `--case/--case-register`）。

**③ 用法（无需改代码）**
```bash
# 比赛形态（默认，纯九格）
bash robot.sh start s_nine --case cases_official30_v2/official_random_05.json \
     --case-register B02_AVAILABLE30_REGISTER.json

# 纯 YOLO 对照
bash robot.sh start s_yolo --detector yolo --case cases_official30_v2/official_random_05.json \
     --case-register B02_AVAILABLE30_REGISTER.json
```

**④ 一次性手续**：改完跑 `scripts/verify_package.py` 刷新 `PACKAGE_MANIFEST.json`。
（`tcei_stack/BUILD_MANIFEST.json` **不受影响**——它只覆盖 `tcei_stack/` 下 36 个文件，不含 `harness/`。）

### 为什么这样设计（附带的两个好处）
- **合规**：默认仍是九格，"纯九格 20 分加分"的默认形态不变；`launch.json` 里**记录本轮检测器**→ 每轮可审计。
- **对照**：同一批场景能一键跑两版，直接出"九格 vs YOLO"成绩对比（正是 Q1/Q2 需要的）。

### 备选方案（对比）
| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **① 启动参数 `--detector`（推荐）** | 一眼可见、进 shell 历史、可透传 | 需改 2 个文件 + 刷清单 |
| ② 仅环境变量 `TCEI_DETECTOR` | 改动最小（1 处） | 命令里看不出来，容易忘 |
| ③ 各写一个启动脚本 | 不动现有代码 | 代码重复、维护差 |
| ④ 改 perception.py 默认值 | 不动启动器 | 仍是改代码；且手跑单节点行为会变 |

> 建议：**①为主，②兜底**（flag 优先，未传时读 `TCEI_DETECTOR`，再默认 `nine`）。

### 注意
- `perception.py` 的默认值仍是 YOLO——手工单跑该节点不带参数会走 YOLO。**保持原样**即可，但要在运行手册里写明。
- 纯 YOLO 轮会**加载 YOLO 权重**，**不能作为比赛提交轮**；建议 yolo 轮命名带 `yolo_` 前缀区分。

### 验收标准
1. `bash robot.sh start t_nine`（不带 --detector）→ 走九格；`bash robot.sh start t_yolo --detector yolo` → 走 YOLO，且 **nine 节点没被启动**。
2. 两轮 `launch.json` 里 `detector` 字段分别为 `nine` / `yolo`。
3. `scripts/verify_package.py` **PASS**。
