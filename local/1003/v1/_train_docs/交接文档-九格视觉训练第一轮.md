## 2. 任务背景

### 2.1 比赛要什么

TCEI 2026 机械臂物资分拣赛有个 **+20 分的「九格多模态加分项」**，条件是**必须由九格 FM9G4B-V 大模型自己完成目标识别**，用 YOLO 不算。

原来的控制器方案（`tcei_260920v2`）用 YOLOv8 出框；加分项要把识别环节换成九格。机器人要从俯视相机看到篮子里的物资，回答"最左边的手电筒在哪""剩下的都抓走"这类指令。

### 2.2 模型是什么

**九格 FM9G4B-V**，4B 参数视觉语言模型：

| 项目 | 值 |
|---|---|
| 架构 | `FM9GV`，62 层，hidden 2560 |
| 注意力 | DeepSeek 风格 MLA（`q_lora_rank=768`，`kv_lora_rank=256`） |
| 视觉编码器 | NaViT-SigLIP + `resampler`（64 个 visual query，`embed_dim=2560`，`num_heads=16`，`adaptive=True`，`max_size=(70,70)`，`kv_dim=1152`） |
| 图像切片 | MiniCPM-V 风格，`max_slice_nums=9`，`scale_resolution=448`，`patch_size=14` |
| 定位输出 | 0–1000 归一化，格式 `<box>[x1,y1,x2,y2]</box>` |

权威规格：`九格 BBOX 调用接口文档.txt`、`九格大模型的量化和训练.txt`（本地 `九格视觉训练/` 目录）。**有歧义时以这两份为准。**

### 2.3 与控制器方案的关系

控制器方案里的决策逻辑（`planning_prompt.py`、`observation_view.py` 等 34 个模块）不需要改，只需把"识别"这一环换掉。**但注意：这条对比测试（控制器+YOLO vs 九格视觉）至今一次都没完整跑过**，见第 7.5 节。

### 3.3 诊断结论（本轮实测，**这是本文档最重要的技术内容**）

对 `eval_val200.jsonl` 做的偏移特征分析：

```
dx(中心, 0-1000)  mean= +8.33   std= 24.33
dy(中心, 0-1000)  mean= -2.90   std= 28.73
dw(宽,   0-1000)  mean= +0.95   std=  6.27
dh(高,   0-1000)  mean= +0.43   std= 10.24
```

**怎么读**：

- `dw` / `dh` 的 mean 和 std **都很小** → **框的尺寸学得极准**，模型完全知道物体多大。
- `dx` / `dy` 的 **std 远大于 mean** → 中心位置是**随机误差**，不是系统性偏移。

换算成像素：

```
位置误差 std  x = 31.1 px   y = 20.7 px
物体尺寸中位  宽 35.0 px    高 39.0 px      （mean 34.8 / 36.1，min 14，max 58）
```

**位置误差和物体本身一样大。** 一个手电筒的 GT 框只有 14×23 像素，而误差是 31 像素。

**物体尺寸与精度的单调关系**（决定性证据）：

| GT 框宽 | 样本数 | avg_iou | hit@0.5 |
|---|---|---|---|
| < 20px | 24 | 0.1050 | 0.042 |
| 20–40px | 93 | 0.2737 | 0.151 |
| 40–80px | 83 | **0.3708** | **0.289** |

物体越大，精度越高，**单调上升**。40–80px 桶的 IoU 是 <20px 桶的 3.5 倍。

> **结论**：这不是格式问题、不是坐标基准问题、不是系统性偏移，而是**有效分辨率不足**——物体在画面里太小，模型的空间精度到不了。

### 3.4 已排除的三个方向（**都用实验验证过，别再试**）

**① 坐标基准搞错了？—— 不是。**
若是基准错位，误差会表现为水平方向按图宽压缩、垂直方向按图高拉伸，**两轴变形比例不同**。实测 `dw`/`dh` 几乎为零（尺寸精确），排除。

**② 是图像切片机制（`max_slice_nums=9`）捣乱？—— 不是，切片在帮忙。**
同样 30 张图上的严格对照：

| 配置 | avg_iou |
|---|---|
| `max_slice_nums=9`（默认） | **0.3800** |
| `max_slice_nums=1`（不切片） | **0.1066** |

关掉切片精度**暴跌到 1/3.5**。切片机制是在帮忙。

**③ 推理时裁到篮子 ROI 放大？—— 不行，而且更惨。（本轮新验证）**

想法很自然：物体只有 35px，那就裁到篮子区域（约 411×282）再送模型，等效放大。**实测彻底失败**：

| 输入 | 样本 | avg_iou | hit@0.5 |
|---|---|---|---|
| 全图 1280×720 | 40 | **0.3796** | **0.300** |
| 裁到篮子 ROI 411×282 | 35 | **0.0311** | **0.000** |

**暴跌 12 倍。** 明细显示裁剪后模型输出的框**又小又偏**（例：GT 框 14×23，裁剪后输出 7×9）。

**为什么**：模型是在完整 1280×720 画面上训练的，它内部的切片机制在裁剪图上会走到**与训练时不同的配置**，等于喂了它没见过的输入结构。这和"`slice=1` 暴跌"是**同一个原因**。

> **推论（很重要）**：**这个模型严重依赖训练时那套固定的视觉预处理。推理期的任何取巧——裁剪、改切片、缩放——都会破坏精度。**
> **唯一可靠的杠杆在训练数据，不在推理端。**

### 3.5 一处交叉验证

"全图 40 张" 的 avg_iou 是 **0.3796**，"slice=9 / 30 张" 的 avg_iou 是 **0.3800**。两组独立实验的数字几乎相同，说明评测脚本和统计口径是自洽的，可以把这些数当基准。

#### 3.6.1 第二轮结果：**成功，IoU@0.5 提升 72%**

训练于 2026-09-28 05:20 完成，全程 0 报错，历时约 11 小时。11 个检查点全部生成，最终适配器 382,337,688 字节。

**各检查点在 200 张验证图上的表现**（与第一轮同一批图）：

| 检查点 | parse_rate | IoU@0.5 | avg_iou |
|---|---|---|---|
| **第一轮基线 `qlora_v1`** | 1.0000 | **0.1950** | **0.2937** |

#### 3.6.3 那 10 个崩掉的样本是什么性质

逐一看了中心误差 >100px 的 10 个样本：

- **没有一个是格式问题**：10 个全都只输出了 1 个 `<box>`，解析正常
- **没有框跑到画面外**：都是合法坐标
- **框的尺寸大多还是合理的**（如 GT 48×31、预测 46×37）——**尺寸对，位置完全放错**
- **7 个集中在 `batch_0005` 这一个批次**，2 个来自 `batch_0015`

**性质判定：不是随机噪声，而是在特定图像里模型把 A 物体认成了 B 物体。** 结合 `<20px` 档 `hit@0.5 = 0.000`，机制很清楚——**小物体定位不了，模型就抓错了物体**。几个离群样本的 GT 都是 14×19、15×19、20×14 这种十几像素的小目标。

#### 3.6.4 第二轮的结论：还剩一个瓶颈，且只剩一条路

第二轮把"训练量/容量"这条杠杆用尽了：IoU 从 0.195 提到 0.335，然后进入平台期。**继续加 epoch 不会有收益**（step_21000 之后已经不涨了）。

**剩下的唯一瓶颈是物体太小。** 证据链完整：

1. IoU 随物体尺寸单调上升（<20px 0.128 / 20–40px 0.363 / 40–80px 0.451）
2. <20px 档的 hit@0.5 = 0.000，完全无法定位
3. 崩掉的样本都是小目标被认成了别的物体
4. 位置误差（中位 11px）与物体本身大小（中位宽 35px）仍是同一量级

**因此下一步只有第 7.3 节的"在裁剪图上训练"这一条路了**（训练和推理都用裁剪图，让物体占据更多像素）。这一节现在从"优先级 3"升级为**唯一的主攻方向**。

### 5.4 模型补丁（最容易漏掉的一项）

**症状**：

```
TypeError: FM9GForCausalLM(...) got multiple values for keyword argument 'input_ids'
```

**根因**：模型 `forward` 里 `self.llm(...)` 显式传了 `input_ids=None` 和 `inputs_embeds=vllm_embedding`，上层又通过 `**kwargs` 传了 `input_ids` 进来，撞车。

**补丁内容**：在 `/root/inference/FM9G4B-V/modeling_fm9gv.py` 里找到 `return self.llm(`，**在它前面**插入：

```python
        kwargs.pop("_input_ids_guard", None)
        for _k in ("input_ids", "position_ids", "inputs_embeds"):
            kwargs.pop(_k, None)
```

**一条命令搞定**：

```bash
cp -n /root/inference/FM9G4B-V/modeling_fm9gv.py /root/inference/FM9G4B-V/modeling_fm9gv.py.bak_prepatch; /opt/conda/envs/inference/bin/python3 -c "import io;p='/root/inference/FM9G4B-V/modeling_fm9gv.py';s=io.open(p,encoding='utf-8').read();ins='        kwargs.pop(\"_input_ids_guard\", None)\n        for _k in (\"input_ids\", \"position_ids\", \"inputs_embeds\"):\n            kwargs.pop(_k, None)\n';assert 'kwargs.pop(\"_input_ids_guard\"' not in s,'already patched';i=s.index('return self.llm(');io.open(p,'w',encoding='utf-8').write(s[:i]+ins+s[i:]);print('PATCH OK')"
```

**验证**：

```bash

```

（不要用 `grep -c` 比具体数字——那个标记串出现几次取决于补丁写法，用 `-q` 判断存在性才不会误判。）

### 7.1 优先级 1：检查点筛选（零训练成本，先做）

`qlora_v1/` 里有 **38 个**中途检查点，每个都是完整可用的适配器。**最终那个不一定最好**——中途某个点泛化更好是常见现象。

```bash
cd /root/sft_v2/scripts && for ck in /root/sft_v2/outputs/qlora_v1/step_*; do n=$(basename $ck); [ -f /root/sft_v2/outputs/log_ck_$n.txt ] && continue; /opt/conda/envs/inference/bin/python3 eval_bbox_lora_coco.py --model-dir /root/inference/FM9G4B-V --adapter-dir $ck --coco-root /root/sft_v2/converted/coco --split val --max-samples 200 --predictions-jsonl /root/sft_v2/outputs/pred_ck_$n.jsonl > /root/sft_v2/outputs/log_ck_$n.txt 2>&1; echo "done $n"; done; echo ALL_DONE
```

汇总排名：

```bash
cd /root/sft_v2/outputs && for f in log_ck_*.txt; do r=$(grep -o 'iou@0.50 *: *[0-9.]*' $f | grep -o '[0-9.]*$'); a=$(grep -o 'avg_iou(parsed_only): *[0-9.]*' $f | grep -o '[0-9.]*$'); echo "$r $a $f"; done | sort -rn | head -15
```

### 7.2 优先级 2：**加数据 + 训更久**（真正针对根因）

诊断结论是"随机位置误差 + 物体太小"，而**总优化器更新只有 1458 次**。这两条都指向同一件事：**训练量不够**。

- **数据量**：现在 1200 张。用 `gt_sft_gen.py` 再采 2000–3000 张，合计 3000–4000 张。
- **训练时长**：`EPOCHS` 从 2 提到 **6–10**。`LR` 仍用 `1e-4`（第一轮用的值）。
- **LoRA 容量**：`LORA_R` 16 → **32**，`LORA_ALPHA` 32 → **64**。空间精度可能需要更大容量，建议和"训更久"一起上。


## 8. 坑清单（换机器会原样复现）

**坑 1：JSONL 里坐标必须是像素，不是 0–1000** ⚠️ 最隐蔽

**现象**：训练能跑完、loss 也降，但框的位置系统性不对，而且**官方校验器查不出来**。

**根因**：飞书给的原始方案里 `make_jsonl.py` 把 bbox **归一化到了 0–1000**。但官方手册要求中间格式用**像素 xyxy**。下游按像素读 → x 按图宽压缩、y 按图高拉伸，**两轴变形比例不同**。归一化后的值都 ≤1000，看起来"合法"，**校验器抓不到**。

**修法**：`make_jsonl.py` 的 `--coord pixel` 是**默认值**，不要改。改完用 `selftest.py` 自检：

```bash
/opt/conda/envs/inference/bin/python3 selftest.py
```

**坑 2：相机内参 fy 必须等于 fx**

**现象**：框**偏矮**并**向画面中心缩**。实测手雷框高 40px，真值应 ~52px。

**根因**：场景相机的 film back 是 **4:3**（`hAp/vAp=1.3704`），输出画面是 **16:9**。渲染器按**方形像素**成像——水平 FOV 由 `hAp` 决定，垂直 FOV 由宽高比推出。正确算法是 `fy = fx = focal/hAp*width`，**不是** `focal/vAp*height`。

**正确值**：`fx = fy = 1343.83`，`cx = 640`，`cy = 360`（1280×720）。

**注意**：`gt_sft_gen.py` **文件头注释**里写着旧的错误值 `fy=1035.92`，代码（`Camera` 类）里是正确的 `self.fy = self.fx`。**以代码为准。** 本地的注释已修正，实例上的还是旧的，不影响运行。

**坑 3：accelerate 必须是 0.33.0**

**现象**：4-bit 模型加载后报 `.to` 相关错误。

**根因**：accelerate 1.2.1 的 `dispatch_model` 在单设备 device_map 下直接 `model.to(device)`，而 **4-bit 量化模型不支持 `.to()`**。源码判据：`if (len(set(device_map.values())) > 1) or force_hooks:`。

**修法**：`/opt/conda/envs/inference/bin/pip install "accelerate==0.33.0"`

**坑 4：`lm_head` 和 `resampler` 都要跳过量化**

**现象**：`assert module.weight.shape[1] == 1`（bitsandbytes 抛的）

**根因**：`lm_head` 被量化了。**官方手册只提了 `resampler`，没提 `lm_head`，但两个都必须跳。**

**修法**：`llm_int8_skip_modules=["lm_head", "resampler"]`

**坑 5：`num_workers` 必须是 0**

**现象**：`PicklingError`

**根因**：Dataset 返回的 `FM9GVBatchFeature` **无法 pickle**，DataLoader 子进程回传时崩。

**修法**：`num_workers=0`。会拖慢训练但别无选择。要提速得改 Dataset 返回纯 dict。

**坑 6：`input_ids` 重复传参，报错被 90 行模型 repr 淹没**

**现象**：`TypeError: FM9GForCausalLM(...) got multiple values for keyword argument 'input_ids'`。**要命的是**这个报错前面跟着 **90 行模型结构 repr**，终端里一闪而过，容易被当成"加载正常输出"划过去。

**找错技巧**：grep 不带缩进的行，真正的报错在最后：

```bash
grep -n "^[A-Za-z].*Error\|^Traceback" /root/sft_v2/outputs/train*.log | tail -20
```

**修法**：见 5.4。

**坑 7：补丁必须打在源文件上，缓存副本会被覆盖** ⚠️ 反复踩

**现象**：补丁打了、`grep` 也能看到，但**跑起来还报同样的错**；或改完能跑，隔天又不行。

**根因**：`transformers` 加载本地模型时会把模型目录的代码**复制一份**到 `~/.cache/huggingface/modules/transformers_modules/` 再 import。只改缓存副本，**下次加载会被源文件覆盖回去**。

**修法**：永远改源文件 `/root/inference/FM9G4B-V/modeling_fm9gv.py`，然后清缓存（见 5.4）。

**坑 8：RefCOCO 图片路径要建符号链接**

**现象**：`FileNotFoundError: '/root/sft_v2/converted/coco/val2014/batch0000_000000.jpg'`

**根因**：转换脚本只把图写到 `coco/{split}2014/`，而 RefCOCO 记录里引用 `train2014/xxx.jpg`（相对它自己目录），找不到。

**修法**：

```bash
cd /root/sft_v2/converted/refcoco && ln -sfn ../coco/train2014 train2014 && ln -sfn ../coco/val2014 val2014 && ls -la
```

**坑 9：多行反斜杠命令粘贴到终端会断**

**现象**：`\` 续行的命令粘贴进去只执行第一行，报 `bash: --model-dir：未找到命令`。

**修法**：**永远给单行命令。** 本文档所有命令都是单行的。写给别人也照此规矩。

**坑 10：base64 传输配合 `>` 重定向会清空目标文件**

**现象**：文件传过去变 0 字节，或 `gzip: crc error`。

**根因**：`base64 -d > file` 若输入被截断/损坏，**重定向会先清空文件**，然后写入失败——**原来好的文件被毁掉**。我踩过，直接把训练脚本变成空文件。

**修法**：分块传输 + **每块单独校验 md5**。传完必须比对源和目标的 md5，不要只看字节数。

**更可靠的做法**：走 JupyterLab 的 contents API（`GET/PUT /api/contents/<path>`），它是文本直传、带 size 校验，比终端粘贴可靠得多。PUT 需要带 `X-XSRFToken`（从 `_xsrf` cookie 取），否则报 `'_xsrf' argument missing`。

**坑 11：忘了 `export PATH` —— 两种表现，都会静默毁掉一次训练** ⚠️ 实测踩到

**表现 A（单条命令）**：`ModuleNotFoundError: No module named 'torch'`

**表现 B（启动训练，更危险）**：
```
nohup: 忽略输入
run_bbox_lora.sh: 行 42: torchrun：未找到命令
```
日志只有两行就结束了，退出码 127。**如果不看日志，会以为训练已经启动**，等几小时才发现什么都没跑。

**根因**：新开的 shell 没有激活 conda 环境，PATH 里既没有 `torch` 所在的解释器，也没有 `torchrun`。

**修法（两种场合不一样，别搞混）**：

- **单条 python 命令**：用绝对路径最省事，任何 shell 都对：
  ```
  /opt/conda/envs/inference/bin/python3
  ```
- **启动训练（`run_bbox_lora.sh`）**：脚本内部调的是**裸命令 `torchrun`**，绝对路径救不了它，**必须导出 PATH**：
  ```bash
  export PATH=/opt/conda/envs/inference/bin:$PATH
  ```
  启动后**务必确认日志里出现了 `Training samples:` 和 `epoch=0 step=0`**，只看到 `nohup: 忽略输入` 就是没起来。

**坑 12：监控脚本自己会数错**

**现象**：训练进度显示 `12857/11664` 超出总数；或训练正常却报 `ANOMALY`；或检查点报"52 个"（实际 38 个）。

**根因**（三个都是我自己的 bug）：
- 算进度时把 epoch 重复计入（`step = ep*5832 + st`），实际应只取 `st`
- 完成判定阈值设成 `done and age > 300`，太严导致误报
- 数检查点时用 `ls qlora_v1 | wc -l`，把 14 个根文件也算进去了（38+14=52）

**教训**：**监控结论必须与日志原始行交叉验证**，不要直接信监控的"异常"或计数。数检查点用 `ls -d .../step_*`。

**坑 13：日志里的 "step" 不等于优化器更新次数**

**现象**：`training_config.json` 写 `epochs=2`、`grad_accum=8`，数据集 5832 条，但日志跑到 `step 11664`。看起来像跑了 16 个 epoch。

**根因**：日志里的 step 是**前向次数**，不除以 grad_accum。真实优化器更新 = 11664 ÷ 8 = **1458 次**。

**为什么要记住这个**：判断"训练量够不够"时要用 1458 这个数（第 7.2 节的依据），用 11664 会高估 8 倍。

**坑 14：ROS 相机发的是 `rgb8`，不是 `bgr8`** ⚠️ 我自己踩的，绕了一大圈

**现象**：`jiuge_live_vision.py` 存下来的帧**整个偏黄橙色**，而仿真画面肉眼看是**蓝色**的（和训练图一致）。桌面色从训练图的 `(177, 223, 235)`（蓝）变成存图的 `(222, 212, 171)`（黄）。

**根因**：脚本里按 `bgr8` 处理，做了 `frame[:, :, ::-1]` 交换红蓝。但实测 `/Jaka/camera/rgb` 的 `msg.encoding` 是 **`rgb8`**，于是蓝桌面被整成了黄橙色。

**危害比"存图颜色不对"严重得多**：这个交换发生在**喂给模型之前**，所以模型拿到的是一张**训练时从没见过的配色**的图，实测效果被严重拖累——当时误以为是"域差异"，其实是自己的 bug。

**修法**（已修）：

```python
if msg.encoding.lower() == 'bgr8':      # 只有 bgr8 才交换
    arr = arr[:, :, ::-1]
```

**排查方法**（怀疑颜色不对时用）：

```bash
source /opt/ros/noetic/setup.bash && cd /root/sft_v2/scripts && /opt/conda/envs/inference/bin/python3 check_encoding.py
```

它会打印实际 `encoding`，并把同一帧按"原样"和"交换红蓝"各存一张、采样桌面色，跟训练图比对，一眼就能看出该不该交换。

**一条通用教训**：ROS 图像话题的编码**必须实测确认**，不能凭约定假设。`rgb8` / `bgr8` 两种都常见，弄反了不会报错，只会让颜色悄悄出错。
