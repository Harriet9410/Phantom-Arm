## 四、三轮改了什么

| 轮次 | 改动的变量 | 结果 |
|---|---|---|
| 第一轮 | 基线：1200 张全图、EPOCHS=2、LoRA r=16 | IoU@0.5 = 0.1950 |
| 第二轮 | **只改训练量+容量**：EPOCHS 2→6、r 16→32（数据不变） | 0.3350（+72%） |
| 第三轮 | **只改数据尺度**：裁到托盘 768×432 再放大回 1280×720（其余同第二轮） | **0.4150**（+24%） |

### 关键诊断结论（都已用实验验证）

1. **根因是物体太小**：物体中位宽 41px，而模型每个视觉 token 覆盖约 46px —— **物体连一个 token 都占不满（实测 0.6 个）**
2. **裁剪+放大把物体 token 占比提到约 2.2 个**，位置量化误差从约 23px 降到约 11px
3. **推理期取巧全部无效**（都已实测否决）：
   - 只裁剪不放大：token 掉到 39（少 11 倍），实测 0.3796 → 0.0311
   - 关切片 `max_slice_nums=1`：0.3800 → 0.1066
   - 调大 `max_slice_nums`（9/16/25/36）：token 数完全不变，无效
   - 提高相机分辨率：面积涨 4 倍但 token 只从 437 涨到 569，**每 token 覆盖反而更差**
4. **训练和推理的视觉预处理必须完全一致** —— 这是三轮里最贵的教训

### 一个操作层面的重要发现

**最优的不是最终适配器，是 `step_27000`（训练 74% 处）**：

```
step_27000   IoU@0.5 = 0.4150   ← 最优
final        IoU@0.5 = 0.3750   ← 退步，过拟合
```

**部署要用 `step_27000`，不要用 final。** 检查点筛选直接多拿了 0.04。

## 六、下一步

### 我建议的（选项 A）

**把 `qlora_crop/step_27000` 接进控制器，做端到端演示。**

配置：`--adapter-dir /root/sft_v2/outputs/qlora_crop/step_27000 --crop 260,51,1028,483 --upscale 1280x720`

理由：
- 总体已基本追平 YOLO，**且在 YOLO 做不了的地方能做**
- 挡着 20 分加分项的不是 IoU 那 0.01，而是"**九格有没有真的在系统里做识别**"
- 接的过程中会暴露真正影响任务成功率的问题（方位判断、抓取精度），比继续调模型更重要

### 可选（选项 B）

再训一轮缩小与 YOLO 在烟雾弹/弹夹上的差距。候选杠杆：
- **加数据**（现在只有 1200 张）
- **训练 resampler**（`TRAIN_RESAMPLER=1`，让视觉编码器适应本任务）
- **更高 LoRA rank**（32 → 64）

成本：约 12 小时、约 17 元。**注意裁剪这条路已经接近极限**（放大倍率最多从 1.67× 提到 1.9×）。
