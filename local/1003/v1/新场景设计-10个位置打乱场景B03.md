# 新场景设计稿：10 个"位置打乱 + 指令配套"场景（B03）

> 设计时间：2026-10-04｜**状态：✅ 已制作并部署（位置 v6 / 姿态 v5），冻结基线十场景真跑进行中**
> 基础：**组成不变**（烟雾弹×2、手电筒、弹夹、手雷，与官方 case 同），只改**摆放位置** + **配套 5 条指令**
> 用途：分变量诊断——把"位置/语义映射"从"姿态"里解耦出来（承接《失败分析-随机场景第3条被拒.md》）
>
> **📌 姿态口径（10/4 复核修正，实测）** —— 此前"姿态=默认场景规矩放法"的说法**不准确**，会误导，按实测改正：
> 1. **B03 姿态来自"官方 case 模板"**（`official_random_01.json` 的 `quaternion_wxyz`），**仅当物体长轴沿世界 Y 时**再叠一个绕**世界竖轴**的 −90° yaw（`Q_YAW_M90`）。竖轴 yaw **不改变物体与重力的关系**（本地 Z 轴方向不变）。
> 2. **实测倾角（本地 Z 轴与世界 Z 的夹角）**：B03 十场景 = **90/180/90/90/90°**（手电筒/弹夹/手雷/烟A/烟B），与**官方 case 模板完全一致** ✓
> 3. **`cases_scramble10/default_poses.json`（scene.usd authored 姿态）与官方 case 姿态相差 16.26°~27.8°**（实测：106.26/103.34/106.26/180/76.66°）——**这就是 v1"看着斜"的来源**；该文件**在生成器里只被 load、从未参与生成**（唯一引用是 register 的 note 文本），**仅作存证**。
> 4. 因此：B03 = **官方 case 姿态（±竖轴 yaw）× 打乱位置 × 配套指令**，姿态侧与官方同族、非 OOD。
>
> **制作结果（10/4）**：10 个 case 全部通过自检（在筐内/间距/**像素质间距 ≥45px**/**指令唯一可满足**/象限一致），已部署到活动包并列于 `cases_official30_v2/`。运行命令见 §六。
>
> ⚠️ **待整理（§六-4）**：生成器的 `poses_path` 参数已成**死参数**（`poses` 变量未被使用）——要么删参、要么在用法里注明"仅存证"。
>
> **📌 位置 v6（10/4 深夜，治本）**：现场实测暴露了**深度分割并核**——某物体与邻居的投影框贴太近时，会被判成 `multiple_body_cores`、`identity_status: ambiguous`，随后**从候选列表消失**，于是点名它的指令必然无解（scramble_03 的"右下方的军用手电筒"就是这么被拒停轮的）。
> 修法：用**真实观测帧标定投影**（`u = 643.5 − 569.3x`、`v = 297.4 + 629.6y`，残差 ≤15.5px；原公式 `643−653x / 280+592y` 斜率差 13%），每象限给 3 个槽位（角槽 + 沿自身横边/竖边内收），搜索后**断言图像内最小框间距 ≥45px**。
> **结果：10/10 通过，最小间距 54.9~65.8px**。对照量纲：旧版 B03 **11.6~19.5px**（现场失败的 scramble_03 恰为 19.5px）；**官方 30 场景中位 34.6px、21/30 低于 45px**（即官方布局本身也不宽裕）。逐字段 diff 确认：只动 `objects` 的位置/bbox 字段，**指令、seed、instance、basket 全未变**。
>
> **📌 位置 v6 顺带修掉一处"必败场景"**：新增断言"**每条指令必须能被恰好一个物体满足**"（依据 `semantics.py:429-449`：带方位词的指令按方位筛同类候选后要求**只剩一个**）后，立刻发现 **scramble_08** 的 `抓取右下方的烟雾弹` 与两个烟雾弹同在右下象限冲突 → 筛完剩两件 → 必然拒单（v5 起就在，只是测试从未跑到第 4 条）。已把 `smoke_bomb_01` 移到 RT（与手雷同象限、类别不同）。**该断言与像素间距断言一并常驻生成器**，布局或指令不满足就直接拒绝生成。

## 一、先划清"能改 / 不能改"（硬约束）

| 项 | 能否改 | 原因 |
| --- | --- | --- |
| **物体位置** | ✅ 任意重排（筐内、物理规则内） | case 的 `objects[].position` 本来就是自由字段 |
| **5 条指令** | ✅ 按新布局重写 | 指令是自然语言，控制台覆盖或写进 case 的 `instructions` 均可 |
| **物体姿态** | ✅ **照抄默认场景的规矩姿态**（不做 30 场景那组躺倒姿态） | 用户定版（10/4）：像官方一样规矩放——默认场景实测烟雾弹立放、手电筒平放、弹夹立放，画面角 0°/90°；姿态值从 `scene.usd` **实读**（见 §二.5） |
| **类别组成** | ❌ **不能"两个手电筒"** | 场景 `scene.usd` 里只有 5 个 prim：烟雾弹**×2**、手雷/弹夹/手电筒**各 1**；case 按 **prim 路径**（`/World/Flashlight`…）引用物体，**不能新增物体**——两个条目指向同一路径会互相覆盖+真值重复，直接坏 |
| **类别集合** | ❌ 4 类固定 | 压缩干粮（CompressedFood）无资产 |

> **"两个手电筒"若坚持要做**：唯一路径是改 `scene.usd`（复制一个 Flashlight prim）——那是**改官方场景资产**，牵动基线校验（`config/image-baseline-manifest.json`）、物理验证与计分口径，**赛前期不建议**。本设计接受"重复的永远是烟雾弹"。
>
> 📌 **姿态原则（10/4 v5 定版——最终）**：保留模板 case 的躺姿（零倾斜、与重力关系不变），**只叠加一个绕世界垂直轴的 90° yaw**，把长轴从"纵向"摆到"横向"（world X）。结果：**五个物体在观察相机里全部是水平长条**，且这种垂直轴旋转**正是训练生成器随机过的扰动**（`gt_sft_gen.py` 只随机 yaw）——所以在训练分布内。
> **迭代史（v1→v5）**：v1 用默认场景沉降姿态（自带 16.3~27.8° 倾斜）✗；v2 模板轴对齐（正视有纵向件）△；v3 全沿 X 但**直接替换四元数**（把物体绕错了轴，且姿态组合偏离"躺姿+yaw"）✗ 实测误标；v4 回退模板（横向/纵向混合）△；**v5 = 模板躺姿 + 垂直轴 90° yaw（全部横向，零倾斜，分布内）✓**。
> **格位**：所有物体深推入象限内部（8 个深位），不压象限分界线；自检含投影防压线断言（u=643−653x, v=280+592y，距中线 ≥25px）。

## 二、位置与姿态规则（生成/摆放必须满足）

沿用 case 模板（official_random_01）的筐参数：`inner_xy`、`wall_margin_m`、`minimum_footprint_gap_m`。

1. 每个物体的 bbox 必须在筐内（`valid_in_basket`：xy 在 inner_xy 内 ±5mm，z 在 2.34~2.43 / <2.55）
2. 任意两物体脚印间距 ≥ 0（`gap = 中心距 − footprint_r_i − footprint_r_j ≥ 0`）——建议留 1 倍脚印宽余量
3. 沉降漂移 ≤ 40mm（31 帧稳定窗）
4. **同象限不放两个需被方位指称的同类物体**（"左上方的烟雾弹"必须唯一，否则数量歧义被拒）
5. **姿态来源（本设计核心）**：`quaternion_wxyz` = **默认场景各 prim 的 authored 朝向**（从 `/root/EAICON/Content/JAKA/scene.usd` 实读，**只读不改**）——即截图里那套规矩放法（立放/平放，0°/90°）。生成器用 `/root/isaacsim/python.sh` 跑一段 pxr 片段，一次 dump 5 个 prim 的 transform + 默认姿态下的 world bbox（bbox 也按默认姿态取，不是模板 case 的躺倒 bbox）

**摆放法**：3×3 网格（左上 LT / 中上 TC / 右上 RT / 左中 ML / 中央 C / 右中 MR / 左下 LB / 中下 BC / 右下 RB）。
被"象限词"指称的物体放**角格**（LT/RT/LB/RB）；被"类别词"直接指称的（手雷、弹夹——各仅 1 件，天然唯一）可放任意格；被"剩余"指称的放剩余格。

## 六、制作清单（**已完成**）与运行方式

1. **dump 默认姿态**（生成器第一步）：用 `/root/isaacsim/python.sh` 跑 pxr 片段，从 `scene.usd` **只读** dump 5 个 prim 的 authored transform + 默认姿态下的 world bbox —— 这就是"官方规矩放法"的姿态与 bbox 来源
2. **生成器**（`test_tools/make_scramble10.py`，**不碰 `tcei_stack/`**）：
   - 以 `official_random_01.json` 为**筐参数模板**，每场景改：`objects[].position / requested_position`；**`quaternion_wxyz / requested_quaternion_wxyz` = 第 1 步 dump 的默认姿态（躺姿 + 绕世界垂直轴 90° yaw，见 §二 v5）**；`bbox_min/max / footprint` 用**默认姿态下的 bbox 平移到新位置**；`reference_xy` 跟随位置
   - `instructions` 换成 §四 明细；`expected_sides` 对应；`case_id=scramble_NN`、`seed=202610110N`、`planner_seed=202610210N`
   - `basket / inner_xy / wall_margin_m / minimum_footprint_gap_m / budget_seconds / coverage_limits` 照抄模板
   - **生成后自检（全是断言，不满足就直接拒绝生成）**：bbox 互不重叠 + 全在 `inner_xy` 内 + **离象限中线 ≥25px** + **图像内任意两物体投影框间距 ≥45px**（防深度分割把两件并成 `multiple_body_cores`）+ **每条指令必须能被恰好一个物体满足**（防 `implicit quantity requires one unambiguous matching object` 拒单）+ 姿态值与 dump 值逐一致
3. **登记**：算 sha256 → 写 `B03_SCRAMBLE10_REGISTER.json`（`case_file=cases_scramble10/scramble_NN.json`）。批量运行器会**逐条校验该 sha**，所以场景文件与登记表必须同时更新
4. **运行（单场景，手动）**：
   ```bash
   bash robot.sh start <栈名>_$(date +%m%d%H%M) --case cases_scramble10/scramble_01.json --case-register B03_SCRAMBLE10_REGISTER.json
   ```
   指令可用 case 自带的（控制台里照抄），或控制台手动覆盖
5. **运行（十场景一次跑完，推荐）** —— 带独立评分的批量运行器，**一条命令、必须写成单行**（多行粘贴曾丢续行符）：
   ```bash
   cd /root/tcei_final_v2_23/tcei_260920v2 && python3 test_tools/run_registered_batch.py --package . --register B03_SCRAMBLE10_REGISTER.json --case-root . --batch b03_sweep_$(date +%m%d%H%M) --task-source custom --all-registered
   ```
   - **`--instructions` 可以省略**：它原本只吃一份扁平指令表（每轮与 `summary.tasks` 严格等值比对），而 B03 每个场景自带 5 条**不同**指令 —— 所以缺省时**改用各场景自带的指令**，并落盘到批次目录（评分核对的就是它实际跑的那一份）
   - 每轮 `start → run → stop`；**场景真值只在每轮结束后读取**用于独立评分，绝不参与抓取选择或改动模型答案
   - 结果写 `$TCEI_RUNS/<batch>/campaign.json`：`results[]` 每案一条；`automatic_verified_rounds` = "状态成功且 `verified_objects == 5`"的轮次数；`independent_physical_rounds` = 物理解算完成的轮次
   - 约 **1.5–2 小时**跑完；**遇到基础设施问题会停下并保留现场**（`status=attention_required`），不会带着坏状态往下跑
   - 批次日录已存在会直接拒绝（`batch already exists; do not replace first-attempt results`）——每次用新的 `$(date +%m%d%H%M)`
   - **建议先在 1–2 个场景上确认一切正常，再挂整批**
6. **验收**：起栈日志 `STRESS_SCENE_READY scramble_NN` + `scene_initialized.json valid:true` + `settling_trace.json` 稳定窗达标；再发指令
7. **测试建议与判读三点**：
   - 顺序：S1（对照）→ S2~S5、S7、S8、S10（象限诊断）→ S6/S9（极端复现）；被拒不纠缠，复位重发一次仍拒则记录跳过
   - ① 是否还出现 `vision/model category disagreement`
   - ② `perception.log` 里 `nine scan: … (settled S, cheap C)` 的 **C 是否随扫描递增**（说明"已鉴定物体走廉价路径"确实在省模型调用）
   - ③ 新增的候选行 `id:类别:身份:面积` 里，被点名过的物体是否**始终 `confirmed`**（不再出现 `ambiguous` → 说明并核已消除）
   - ④ **被拒的指令现在会"跳过并继续"**（`dev_v7_t1_41`）：单条被拒记 `task_rejected` 后本轮继续跑下一条，不再像首次那样一案只看到 1–4 条就停；因此**每案应能看到全部 5 条落点**，批次日志里会出现 `task_rejected_continuing`
