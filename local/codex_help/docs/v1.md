# TCEI 项目总览（v1 修订）

> 原撰写：zxh（2026-10-03）；技术路线补充与现状核对：2026-10-06。本文是项目讲解；实际运行以服务器活动包 `/root/tcei_final_v2_23/tcei_260920v2` 的冻结清单和回合记录为准。核对时服务器 `BUILD_MANIFEST.json` 为 `dev_v7_t1_46`，标记 `development_only=true`、`live_grasp_validation_pending=true`，不能据此称已完成最终比赛验收。

## 项目要解决什么

TCEI 的任务是让机械臂从篮内按中文自然语言指定的对象和方向抓取物资，交付到左/右传送带，并保留可核对证据。场景含五件物品、四个已适配类别：两枚烟雾弹，以及弹夹、手电筒、手雷各一件。项目的难点不是单独识别出物体，而是**在变化的布局中把“指令所指对象 → 可抓姿态 → 安全路径 → 真实落点”闭环对应起来**。

## 整体技术路线

```text
官方镜像 Isaac Sim / EAICON / ROS Noetic / 相机与机械臂
   ↓ RGB-D、相机内参、关节/夹爪物理反馈
感知：深度几何提案 + 九格视觉分类（默认）+ 跨帧身份跟踪
   ↓ 候选对象、类别、画面位置、朝向、不确定区
理解：FM9G4B-V + LoRA；编号全图上选择指令所指对象
   ↓ 程序做指令语义、空间关系、身份和时效校验
执行：抓取姿态候选 → 仿真预览/IK/碰撞与工作区约束 → 机械臂抓放
   ↓ 抬升接触、对象搬运、传送带落点与安全停止证据
评估：逐任务事件、RGB-D、标量记录、summary 和独立复核
```

实现分为四个长期运行节点：`sim_with_feedback.py` 包装官方仿真与物理反馈，`perception.py` 处理 RGB-D 并发布候选，`nine_node.py` 执行九格分类请求和语义选择，`controller.py` 处理抓放状态机。`robot.sh` 是操作入口，`scripts/` 与 `harness/` 负责初始化、起栈、回合准入、进程与资源校验；`run_episode.py`/`episode_driver.py` 统筹指令和事件；`evaluation/` 留存证据。控制台 B 只是 `robot.sh run` 的图形前端，不是第二套抓取算法。

**训练路线**：用带标注的图像对 FM9G4B-V 做 QLoRA 适配，运行时在分类请求上加载 `qlora_crop/step_27000`；选择指令目标时关闭该适配器，仍用基座语义能力。`nine_classify.py` 将深度几何提案和模型分类结合。默认 `--detector nine` 不加载 YOLO 权重；`--detector yolo` 是检测器对照，但九格语义节点仍在。训练检查点和历史评测只说明训练过程，不能代替当前场景抓取表现。

**场景路线**：默认场景用于基本链路；B03 十个场景改变物体位置、保持横平竖直，更接近已知比赛形态，且各 case 有对应 `instructions`；B02 三十个带随机角度的场景是扩展泛化挑战。B02 目录沿用 `official30` 历史名字，不应据此认定为官方赛事题库。优先按 B03 的逐场证据评价，再单列 B02；不能把两组通过率混算。

**动作路线**：通过目标重绑定、几何抓取候选、轨迹与间隙检查、预览和闭环反馈来选择可行姿态。速度限制固定时，优化目标可以是减少不必要转折、关节翻腕和停顿；这些目标必须服从碰撞、接触、物体保持与停止约束。当前代码是有限候选筛选，没有证据证明所有新场景都达到全局最优姿态路线。出现“向右搬运前先向左”的现象，应先定位实际是预抓、避障、IK 解支还是搬运段，再据轨迹证据判断是否可消除。

## 如何判断“做成了”

一轮至少要回答：指令是否与当前场景匹配？九格选中的是哪个具体实例？目标重新观测是否一致？抓取姿态和轨迹是否通过约束？抬升后是否真持物？释放后物体是否在正确侧传送带？证据记录与安全停止是否完整？这几项必须对同一回合、同一冻结版本核对。仿真通过是比赛准备的证据，实际评分口径仍由赛事规则和裁判决定。

### 知识

#### LoRA / QLoRA / PEFT 是什么

##### 1\. 背景：为什么要“微调”

基座模型（FM9G4B\-V，8\.5GB）是别人在通用数据上预训练好的，**不认识我们的烟雾弹、弹夹、手电筒**。要让它干我们的活（看图 → 输出物体框），得用我们自己的 1200 张标注图再“教”它一遍，这个过程叫**微调（fine\-tuning）**。

**全量微调**（把 62 层、几十亿参数全部重训一遍）的问题：

- 要存一整份新模型（又是 9GB）

- 显存要够（24GB 卡基本不够）

- 每换一个任务就得存一个 9GB 副本，非常浪费

##### 2\. LoRA：不训全部，只训一小块“增量”

**LoRA = Low\-Rank Adaptation（低秩适配）**。核心想法一句话：

> 冻结原来的权重 `W`（一个都不改），在旁边加一对小矩阵 `A` 和 `B`，只训这两个小的**。**
> 
> 

forward 时算的是 `W + B·A`——原来的知识（`W`）原封不动，新学的知识全装在 `B·A` 里。因为 `A`、`B` 很“瘦”（低秩），参数量比 `W` 小几个数量级，所以：

- 训出来的增量只有**几百 MB**（本项目就是那个 382 MB），不是 9GB

- 想换任务，就把这一小块**拆下来换一块**（所以叫 **adapter，适配器**——可插拔）

- 基座可以多任务共享，一份基座配多个适配器

几个必懂的**超参**：

|词|含义|本项目取值|
|---|---|---|
|**`r`****（rank，秩）**|那对小矩阵有多“宽”。越大越能学、也越大越容易过拟合|**32**|
|**`alpha`****（缩放）**|控制新学部分对输出的影响强度，常按 `alpha/r` 折算|**64**|
|**`dropout`**|训练时随机丢弃，防过拟合|0\.05|
|**`target_modules`**|把 `A/B` 挂到哪些层上（挂得越多越大）|**8 个 MLA 层**|

> **这就是为什么是 382 MB 而不是 9 GB**：LoRA 只存那对 `A`/`B`，不存基座。
> 
> 

##### 3\. PEFT / adapter / checkpoint —— 一堆近义词

- **PEFT** = Parameter\-Efficient Fine\-Tuning（参数高效微调）的**统称**，LoRA 只是其中一种（还有 DoRA、RSLoRA 等，本项目没用）。

- **adapter（适配器）** = LoRA 训完产出的**那组小权重文件**。本项目里就是 `adapter_model.safetensors` \+ 它的 config。

- **checkpoint（检查点）** = 训练过程中**每隔 N 步存一次**的快照。所以一个训练目录里会有 `step_9000`、`step_15000`、…、`final` 好几份。本项目 `save_every=3000` → 12 个检查点。

##### 4\. QLoRA：先把基座压成 4bit，再挂 LoRA

**QLoRA = Quantized LoRA（量化版 LoRA）**。在 LoRA 基础上多做一件事：

> **加载基座时用 4bit 量化（NF4），把 9GB 的基座压到约 2\~3GB 显存，然后依然只训 LoRA 增量。**
> 
> 

- **量化**：把权重从 16bit/bf16 压成 **4bit** 存储（用 `bitsandbytes` 库，格式叫 **NF4**）。精度略降，但省大量显存。

- 训练时基座是**冻结的 4bit**，只有 LoRA 的 `A`/`B` 用高精度被更新。

- 本项目 `training_config.json` 里 **`load_in_4bit: true`** 就是它——**这也是“训练绝不改基座”的机制保证**：基座根本就是以量化只读形式加载的，改不了。

> **一句话对比**：LoRA = 只训一小组增量；**QLoRA = LoRA \+ 基座 4bit 量化**。本项目用的是 QLoRA。
> 
> 

##### 5\. 推理时发生了什么（“挂载”）

训练完，那 382 MB 的适配器要在**运行时**叠到基座上才生效：

```Python
PeftModel.from_pretrained(基座, 适配器目录)   # 把 A/B 叠上去，等价于 W + B·A
```

- 基座**只被读取**，文件不变 → 这就是"9\.29 训练没改模型本体"的最终答案。

- 还能临时关掉：\`disable\_adapter\(\)\` 让模型退回纯基座行为。本项目正是用它在"选块推理"时关掉适配器，只在"分类/出框"时启用。
