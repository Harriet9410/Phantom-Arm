## 先看完整任务：一条指令怎样变成动作

以“抓取右下方的弹夹，放到右侧传送带”为例，程序不能只识别“弹夹”三个字。它要先在当前画面里找到物体，确认哪个弹夹处于右下方，再算出机械臂能否接近、能否夹稳、搬运时会不会碰撞，最后核对它是否真的落在右侧传送带。

```text
自然语言指令
  → 观察当前 RGB-D 画面
  → 得到带位置、类别、身份和不确定性的候选物体
  → 九格模型选择“指令所指的具体那一件”
  → 程序校验类别、方位、目标身份和画面时效
  → 生成并筛选抓取姿态、机械臂路径
  → 仿真机械臂抓起、搬运、放下
  → 用图像、夹爪、关节与传送带证据核验结果
```

这里有两类判断：模型回答“想抓哪件”，代码和物理反馈判断“这个回答能否执行、执行后是否成功”。二者缺一不可。更细的文件调用顺序见《代码与技术路线导读》；下面先讲每部分在整个项目中的作用。

## 关于场景与题目

**场景**是 Isaac Sim 中的机械臂、篮子、物体和传送带；**题目**是某个场景摆位加对应的自然语言指令。场景看着相似，也可能因物体位置改变而使“左上方”“最左方”“剩余”指向不同对象，因此不能把默认场景的五条话直接用于所有布局。

项目把场景 JSON 和登记表配对。`--case` 指定摆位，`--case-register` 指定登记表；启动时会核对文件散列、case_id 和种子，再检查摆放是否稳定。题目真值用于测试后的独立核验，不能在执行时暗中告诉视觉或控制器答案。

| 组别 | 用来回答什么问题 | 解释边界 |
|---|---|---|
| 默认场景 | 基本链路能否跑通？ | 只有一套原始布局，不能证明泛化。 |
| B03 十场景 | 位置变化时，是否仍能按本场指令正确选物并抓放？ | 物体保持默认平放态；这是目前更接近已知比赛形态的重点。 |
| B02 三十场景 | 带随机角度的摆放下，系统是否还有鲁棒性？ | 属扩展挑战；目录名虽有 `official30`，不应据此当作官方题库。 |
| B01 三十场景 | 旧失败案例是否复现或修复？ | 用于回归，测试口径与 B03 不同。 |

B03 的生成脚本 v5 实际写入平放姿态或绕竖直轴的 90° 调整；部分 case 仍留有旧模板的“随机 yaw”文字和 `yaw_delta_degrees` 字段。读姿态要看 `quaternion_wxyz` 和启动后的物理场景，不能只看这两个旧字段。

## 关于视觉：机械臂怎样知道“东西在哪”

俯视相机提供**彩色图**和**深度图**。彩色图帮助辨认类别和外形；深度图估计物体相对相机的距离，也帮助把物体与背景、机械臂遮挡区分开。相机内参告诉程序怎样把像素坐标换成三维方向。RGB、深度和内参必须属于相近时刻；如果拿上一帧的位置去抓这一帧的物体，就可能抓空。

当前默认检测链先用深度几何提出可能的物体区域，再向九格模型请求分类；`perception.py` 合成候选并发布，`perception_tracking.py` 尝试跨帧维持“同一件物体”的身份。候选不只有类别，还包含框、深度、位置、朝向、时间和不确定性。遮挡或分类冲突时，正确行为是保留“不确定”并继续观察，不能为了凑齐五件而编一个确定答案。

`--detector yolo` 可用于对照实验。默认九格模式不加载 YOLO 权重，但仍依赖深度几何和程序规则；“不用 YOLO”不等于“只让大模型看图凭感觉抓”。三位组员写的旧视觉与 ROS 资料展示早期 YOLO 节点链路，有助于理解相机话题与坐标转换，但不能照搬为当前运行链。

## 关于指令理解：从“弹夹”到“右下方这一个”

类别词只回答“是什么”，方位词回答“是哪一个”。九格节点会收到带编号的完整画面、候选列表和原指令，再返回目标选择。完整画面保留左/右、上/下、最左/最右等关系；局部裁剪图可帮助看清外观，却不能单独证明全局方位。

模型回答后，`semantics.py` 还会检查：类别是否匹配；指定的象限或极值是否成立；候选是否仍在篮内；“剩余物品”是否已由前序任务账本排除；图像是否足够新；未知区域是否可能推翻当前选择。`semantic_repair.py` 可以把拒绝原因反馈给模型重答，最终仍不合规则拒绝任务。

这层程序校验很重要：模型说得像人话，并不代表选中了场景中真实存在的那一件。当前回合代码对**计划接受前**的语义拒绝会尝试结清该任务；能确认物体未被触碰时可继续下一条，已有抓放证据或账本无法了结时停止。具体分支以对应冻结版本的 `episode_driver.py` 为准。

## 关于机械臂：为什么不能直接走一条固定路线

抓取需要同时确定**抓哪一点、夹爪朝向、从哪里接近、抬多高、怎样搬运、在哪里释放**。同一件弹夹换了位置，机械臂关节的可达姿态、篮沿间隙、邻近物体和回程路线都会变。`grasp_candidates.py`、`controller.py` 与仿真预览负责给出有限候选、淘汰不可行方案；`sim_with_feedback.py` 把可接受的命令交给 Isaac 执行并回传物理状态。

动作速度有约束时，“更丝滑”主要指减少无意义绕行、关节翻腕、急停再起和姿态突变，同时不牺牲碰撞间隙与抓持稳定。抓起后先向左再去右带，可能是接近/避障、所选 IK 解支、预览起点或真正搬运路线造成，不能只凭最终画面断定哪一步错。项目当前是有限候选和反馈筛选，**没有证据证明对所有场景都求到了全局最优路线**。

抓住也需要证据。夹爪闭合不等于夹中物体；试抬后的接触、画面中的物体移动、持物过程是否掉落，以及释放后的传送带观测，分别检验不同阶段。任何一环缺失，结果可能是“待核验”而非成功。

## 关于 ROS、Isaac 与操作入口

Isaac Sim 负责仿真物理与相机/关节反馈；ROS 话题在进程之间传递图像、候选、计划、动作命令和状态。可以把 ROS 理解为系统的消息通道：某个节点发布消息，其他节点订阅，但话题存在并不代表消息内容正确或时间足够新。

当前包长期运行的四个节点是：`sim_with_feedback.py`（仿真与反馈）、`perception.py`（感知）、`nine_node.py`（九格推理）、`controller.py`（动作控制）。`robot.sh start` 只启动与预热，执行开关仍关闭；`robot.sh run` 做准入检查、开启证据记录、按预算执行一个回合；`status/cancel/stop` 分别用于查看、受控取消和收尾。B 入口控制台只是把人工输入写成 JSON 并调用同一 `run` 链路。

不要把训练脚本、可视化窗口、旧 ROS 节点和当前四节点混为一谈。它们有的负责产出权重，有的只读展示，有的属于历史方案；能否驱动本轮机械臂，以实际栈 `launch.json` 中的进程命令为准。

## 关于结果：成功要拿什么证明

每轮应当保存指令原文、入场候选、运行版本、逐条事件、图像与深度、标量反馈、汇总和监督器收尾。`episode/summary.json` 说明程序如何判定；`rgbd/`、`scalars/` 和节点日志让我们复核“选对没有、抓住没有、是否掉落、落点在哪”。`supervisor_finished.json` 再说明记录器是否完整关闭、执行开关是否收回和停止状态是否需要人工关注。

一次演练至少分开统计：**已发起、语义拒绝、抓取失败、放置待核验、物理交付已核验**。不能把窗口弹出、篮子变空或某条日志写着 `task_succeeded` 单独当成比赛得分；更不能把 B03 与 B02 混成一个成功率。最终评分仍由比赛规则与裁判口径决定。

## 项目目前的边界

这是按现有代码和可读证据解释系统怎么工作，不是“全场景最优”或“最终参赛验收通过”的证明。当前已知示例覆盖四类五件，未公开题目、其他资产和新布局需要另行验证。服务器上的开发清单仍可能随团队工作变化；学习时应先核对 `BUILD_MANIFEST.json`、栈 `launch.json` 与回合 `runtime_manifest.json` 是否指向同一版本。

### 知识

#### LoRA / QLoRA / PEFT 是什么

##### 1\. 背景：为什么要“微调”

基座模型（FM9G4B\-V，8\.5GB）是别人在通用数据上预训练好的，**不认识我们的烟雾弹、弹夹、手电筒**。要让它干我们的活（看图 → 输出物体框），得用我们自己的 1200 张标注图再“教”它一遍，这个过程叫**微调（fine\-tuning）**。

**全量微调**（把 62 层、几十亿参数全部重训一遍）的问题：

- 要存一整份新模型（又是 9GB）

- 显存要够（24GB 卡基本不够）

- 每换一个任务就得存一个 9GB 副本，非常浪费

##### 2\. LoRA：不训全部，只训一小块“增量”

**LoRA = Low\-Rank Adaptation（低秩适配）**。核心想法一句话：

> 冻结原来的权重 `W`（一个都不改），在旁边加一对小矩阵 `A` 和 `B`，只训这两个小的**。**
> 
> 

forward 时算的是 `W + B·A`——原来的知识（`W`）原封不动，新学的知识全装在 `B·A` 里。因为 `A`、`B` 很“瘦”（低秩），参数量比 `W` 小几个数量级，所以：

- 训出来的增量只有**几百 MB**（本项目就是那个 382 MB），不是 9GB

- 想换任务，就把这一小块**拆下来换一块**（所以叫 **adapter，适配器**——可插拔）

- 基座可以多任务共享，一份基座配多个适配器

几个必懂的**超参**：

|词|含义|本项目取值|
|---|---|---|
|**`r`****（rank，秩）**|那对小矩阵有多“宽”。越大越能学、也越大越容易过拟合|**32**|
|**`alpha`****（缩放）**|控制新学部分对输出的影响强度，常按 `alpha/r` 折算|**64**|
|**`dropout`**|训练时随机丢弃，防过拟合|0\.05|
|**`target_modules`**|把 `A/B` 挂到哪些层上（挂得越多越大）|**8 个 MLA 层**|

> **这就是为什么是 382 MB 而不是 9 GB**：LoRA 只存那对 `A`/`B`，不存基座。
> 
> 

##### 3\. PEFT / adapter / checkpoint —— 一堆近义词

- **PEFT** = Parameter\-Efficient Fine\-Tuning（参数高效微调）的**统称**，LoRA 只是其中一种（还有 DoRA、RSLoRA 等，本项目没用）。

- **adapter（适配器）** = LoRA 训完产出的**那组小权重文件**。本项目里就是 `adapter_model.safetensors` \+ 它的 config。

- **checkpoint（检查点）** = 训练过程中**每隔 N 步存一次**的快照。所以一个训练目录里会有 `step_9000`、`step_15000`、…、`final` 好几份。本项目 `save_every=3000` → 12 个检查点。

##### 4\. QLoRA：先把基座压成 4bit，再挂 LoRA

**QLoRA = Quantized LoRA（量化版 LoRA）**。在 LoRA 基础上多做一件事：

> **加载基座时用 4bit 量化（NF4），把 9GB 的基座压到约 2\~3GB 显存，然后依然只训 LoRA 增量。**
> 
> 

- **量化**：把权重从 16bit/bf16 压成 **4bit** 存储（用 `bitsandbytes` 库，格式叫 **NF4**）。精度略降，但省大量显存。

- 训练时基座是**冻结的 4bit**，只有 LoRA 的 `A`/`B` 用高精度被更新。

- 本项目 `training_config.json` 里 **`load_in_4bit: true`** 就是它——**这也是“训练绝不改基座”的机制保证**：基座根本就是以量化只读形式加载的，改不了。

> **一句话对比**：LoRA = 只训一小组增量；**QLoRA = LoRA \+ 基座 4bit 量化**。本项目用的是 QLoRA。
> 
> 

##### 5\. 推理时发生了什么（“挂载”）

训练完，那 382 MB 的适配器要在**运行时**叠到基座上才生效：

```Python
PeftModel.from_pretrained(基座, 适配器目录)   # 把 A/B 叠上去，等价于 W + B·A
```

- 基座**只被读取**，文件不变 → 这就是"9\.29 训练没改模型本体"的最终答案。

- 还能临时关掉：\`disable\_adapter\(\)\` 让模型退回纯基座行为。本项目正是用它在"选块推理"时关掉适配器，只在"分类/出框"时启用。

## 模型章节核对注记

上面的“关于大模型”保留原稿讲法。学习时另注意三点：

1. **4bit 量化不自动保证权重只读。**“基座不参与训练”要由训练代码的参数冻结设置与训练记录共同证明；量化主要是省显存。
2. **适配器不是只有一个文件。**主要增量权重在 `adapter_model.safetensors`，实际加载还依赖同目录配置等文件。原文的 382 MB、9.03 GB、1200 张等数字属于当时的训练快照，引用前应核对当前文件与配置。
3. **“最优检查点”和“唯一不可再生”是当时的项目判断。**要证明最优需说明评测集与指标；官方镜像或备份若仍可取得，基座并非物理上不可恢复。这些判断不影响“基座 + 补丁 + 适配器”三层结构的学习价值。
