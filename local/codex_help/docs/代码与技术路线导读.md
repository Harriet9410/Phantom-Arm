## 先读这张图

```text
操作员 / 题目 JSON
   ↓ robot.sh → scripts/start.py → harness/launch_stack.py
Isaac Sim + ROS 话题  ←→  perception.py（九格默认 / YOLO 对照）
   ↓ 相机 RGB、Depth、内参       ↓ 候选、身份、图像
九格模型 nine_node.py ← nine_classify.py（分类请求）
   ↓ 经语义校验的目标与放置侧
run_round.py → run_episode.py → episode_driver.py → controller.py
   ↓ 预览 / 轨迹 / 夹爪命令                     ↕ 状态与物理反馈
sim_with_feedback.py（包装官方仿真控制）→ 机械臂、传送带
   ↓
RGB-D / 标量 / 事件 / summary / supervisor_finished
```

这是两条闭环：**信息闭环**从同步图像、候选跟踪、九格分类和语义选择到再次观察；**动作闭环**从抓取姿态候选、仿真预览、关节轨迹与夹爪反馈到抬升和落带验证。九格模型给目标选择与类别证据，不能直接下发未经程序验证的运动命令。`robot.sh start` 只起四个节点并预热，执行开关保持关闭；`run` 才计时、开记录器、允许运动。

## 为什么旧资料与现状不同

下载目录中的《关于视觉的代码》《关于ros的代码》《关于九格的代码》讲的是训练九格视觉之前的旧链路：`isaac_yolov8.py → isaac_scale.py → isaac_yolov8.cpp → isaac_grasp.cpp`。它们适合学习 ROS 发布/订阅、RGB-D 投影及早期方案演化，**不应当作当前包的调用图**。现包的运行入口是 `arm/robot.sh`；`harness/launch_stack.py` 同时启动 `sim`、`controller`、`perception`、`nine` 四节点。默认 `--detector nine` 时 `perception.py` 不加载 YOLO 权重；YOLO 是 `--detector yolo` 对照模式，但九格语义节点仍运行。旧 ROS 工作区及官方仿真源码仍是环境依赖，不能因此推断旧抓取节点参与本包执行。

本文沿用 v1 的项目全貌，只把镜头拉近到“每个程序文件负责什么、谁调用谁”。模型为什么训练、基座/补丁/适配器是什么，直接读 v1 原作者的“关于大模型”；这里不重复改写那部分。

## 第一章：读这套代码，先分清进程、函数和消息

这套系统不是从头到尾由一个 Python 函数调用完成。`run_round.py` 是监督进程，`run_episode.py` 是回合进程；仿真、控制、感知、九格各自运行。进程之间主要通过 ROS 话题传 JSON 字符串或图像，因而“`EpisodeDriver` 调用九格”是业务上的说法，代码上是它向 `/tcei/request` 发布消息，`Nine.on_request()` 接收。理解这一点，才能解释为什么一条任务会有多个日志、多个时间戳、多个失败出口。

可以把源码按职责分为五层：① `robot.sh` 和 `scripts/` 接收人输入、校验环境并管理进程；② `perception.py`、`nine_classify.py`、`nine_node.py` 把传感器数据变为目标候选和语义选择；③ `episode_driver.py`、`mission_ledger.py` 维护整轮任务、依赖和预算；④ `controller.py` 决定动作阶段和候选姿态，`sim_with_feedback.py` 对每段路线求解、执行并回报；⑤ `evaluation/`、`test_tools/` 记录和离线检查。上一层提出意图，下一层仍会检查自己的准入条件；某层接受不等于物体已经交付。

阅读一个功能时，依次回答四个问题：**输入从哪里来，输出送到哪里，拒绝条件是什么，成功由谁证明**。例如九格输出一个候选编号只是模型答案；`semantics.py` 校验后才可能产生计划；`controller.py` 还要重新绑定现时目标；只有抓取和落带的物理证据经过账本，才可能成为已验证交付。这个顺序贯穿下面各章。

### 1.1 核心消息契约

| 通道或数据 | 生产者 → 消费者 | 读它时要核对什么 |
|---|---|---|
| `/Jaka/camera/rgb`、`depth`、`camera_info` | 仿真 → `perception.py` | RGB/深度是否同一仿真时刻，内参和尺寸是否匹配；深度单位是否已转为米。 |
| `/tcei/classify_request`、`classify_result` | `nine_classify.py` ↔ `nine_node.py` | `request_id` 是否对应、分类是否超时或冲突；这是物体类别识别，不是机械臂计划。 |
| `/tcei/candidates`、`annotated_image` | `perception.py` → 九格、回合、控制 | 候选的帧内 `id`、跨帧 `stable_id`、类别、几何、新鲜度、未知区。 |
| `/tcei/request`、`/tcei/plan` | `EpisodeDriver` → 九格 → 控制器 | `round_id/task_id/request_id`、指令、目标身份、源帧与现帧、放置侧。 |
| `/tcei/nine_status`、`/tcei/task_status` | 九格、控制器 → 回合 | 模型是否真正推理、计划是否发布、抓放证据是否形成、任务为何停止。 |
| 预览、执行、停止相关话题 | `controller.py` ↔ `sim_with_feedback.py` | 预览 ID 绑定、真实起始关节、规划结果、运动反馈和实测停止。 |

上表刻意只列主要通道；具体发布/订阅声明以源码为准。**`id` 是一帧中的序号，不是物体永久身份**；`stable_id` 才供跨帧账本追踪。`frame_id` 标识场景观测版本，`request_id` 串起一次语义请求、计划和动作。相机 ROS stamp 用仿真时钟配对；`observed_at` 等墙钟用于接收新鲜度；`monotonic` 用于本进程预算与超时。三种时间不可互换，尤其不能把图像序号当物体身份或把墙钟差当仿真帧差。

## 第二章：从启动到计时，谁拥有执行权

先读 `robot.sh`：它只是把 `start/run/status/cancel/stop` 等命令分发给脚本。`scripts/start.py` 调用 `harness/launch_stack.py`，后者先查资源、冻结文件哈希、场景登记信息和环境，再起仿真、控制、感知、九格四节点，写出独立栈目录。针对登记场景，`harness/original_layout_sim.py` 负责初始化摆位。启动末尾的 `probe_no_action.py` 核对就绪阶段没有动作；此时控制与九格的执行开关仍关闭。**节点在线只证明可连接，不证明本轮动作获授权。**

`scripts/run_round.py` 才处理一轮任务。它验证指令、栈和场景新鲜度、冻结哈希、空载夹爪和证据存储空间，保存入场画面与运行清单，开启 RGB-D/标量记录，然后打开执行开关并启动 `run_episode.py`。`run_episode.py` 建立 ROS 传输、做回合内预检、创建 `EpisodeDriver`，结束后写事件和摘要。`evaluation/instruction_console.py` 的 B 窗口是这个入口的图形操作层，不另有一套机械臂策略。

`EpisodeDriver.run()` 在执行权确认后建立 `MissionLedger`，记录 `judge_started`，从此共同预算开始。随后即使是在等 ROS 连接、准备观测、等模型标签或收尾，时间仍在走。驱动器先发 `/tcei/prepare_observation`，等待控制器接受、开始和完成；再按指令生成 `task_id/request_id` 并逐条发布 `/tcei/request`。超时、取消和任务失败会进入受控停止与证据收尾。代码默认预算参数为 600 秒，但这是软件中的回合预算，赛事规则与本次服务器实际参数仍须另行核对。

理解“**准入—动作—收尾**”三个阶段，能避免两种误读：看到四节点 `ready` 便认为已经开始计时；或看到 `task_succeeded` 便认为整轮已完成。前者还没有执行权，后者仍要看后续任务、账本和监督器。

## 第三章：一张 RGB-D 图如何变成可抓对象

`perception.py` 订阅 RGB、深度和相机内参，用近时同步器配对 RGB-D。`on_frame()` 接收帧，`process_latest()` 控制处理频率，`process_frame()` 执行主体逻辑。它先检查帧时效和图像尺寸；`16UC1` 深度乘 `0.001` 转成米，`32FC1` 本来按米读取，其他编码报错。随后按检测模式调用 `NineRotationDetector.detect()` 或 `rotation_detector.detect()`。默认九格路线先从深度/外观提出区域，再经 `nine_classify.py` 请求九格给类别；不能把“九格视觉”理解为让模型凭一句话直接控制所有感知几何。

候选的像素中心 `(u,v)` 与深度 `z` 经内参反投影：`x_camera=(u-cx)z/fx`，`y_camera=(v-cy)z/fy`；再由代码中的相机到场景变换得到三维 `position`。这就是“画面里偏了几个像素”为何可能造成抓取点偏移。这里还有 `world_position` 供几何审计，历史抓取标定另在 `core.calibrated_grasp()`；两种坐标不能看见名字相似就直接互换。深度补丁会剔除无效点，主体类还可能用 `body_center()` 修正盒框中心；透视、支撑面和遮挡均会影响最终姿态。

`CandidateTracker.update()` 在帧与帧之间维护 `stable_id`，同时给身份状态和关联理由。检测得到的 `id='1'` 下一帧可能属于另一个物体；若身份不确定，语义层或动作层应等待新观测。`unknown_regions`、`sensor_issues`、`coverage_complete` 表示场景是否可被完整解释，而不只是为了在画面上画橙框。特别是“最右”“全部”“剩余”等指令，一个未知遮挡区可能改变答案；单个已见目标很清晰也不代表集合完整。

**读代码练习：**从 `process_frame()` 追踪一个候选的 `pixel → depth → position → class → id/stable_id → /tcei/candidates`，逐项写下单位和有效条件。若框可见但候选没进入计划，先看它是否被区域提案、深度有效性、类别、置信度、身份或完整性门控挡住；不要先认定模型答错。

## 第四章：九格模型做两种事，语义守卫做第三件事

同一 `nine_node.py` 承担两个请求流。`on_classify_request()` 处理局部分类：收到 `nine_classify.py` 的请求后，在模型锁内推理，回 `/tcei/classify_result`，**不发布动作计划**；当前默认分类客户端显式传 `grounding=false`，因此关闭 grounding 适配器。`run()` 处理任务语义：等候与请求绑定的新场景和图像，构造 `planning_prompt.py` 提示，记录 `infer_started/model_answer`，再把答案交给 `semantic_repair.infer_validated_selection()`；其模型调用也包在 `_adapter_off()` 中。也就是说，节点虽可装载可选 grounding LoRA，**这两条默认路径都不用它参与推理**；只有其他明确传 `grounding=true` 的分类请求才可能启用。是否装载以及实际调用配置仍要从该次运行参数/日志核对。同一模型被两个用途共享，模型锁避免并发推理互相干扰，但也意味着分类积压会占回合时间。

语义层的三个主要入口应分开读：`audit_instruction()` 把中文任务解析成类别、数量、空间关系和左右传送带等约束；`parse_model_plan()`/`parse_compact_selection()` 把模型文本变成规定格式；`validate_selection()` 才拿候选、几何和任务账本审查答案。它会拒绝不存在的编号、类别不符、深度或置信度不足、身份不确定、非法来源、方位/极值/数量不一致等。`semantic_repair.py` 可在预算内带拒绝原因重新问模型，但重问之后仍须重验。验证通过后，九格在发布 `/tcei/plan` 前又核对现时场景、目标关联和截止时间。因此“模型原文正确”仍可能因画面过期而不能执行。

可以用**示意**理解这层，而不要把下列 JSON 当作可直接提交的真实协议：

```text
指令：把最右边的弹夹放到右侧传送带
场景：帧 42 有候选 id=1、id=2；两者类别均为 Magazine，跨帧身份已确认
模型选择：id=2，side=right
程序复核：id=2 确实是同类唯一最右；未知区不会改变极值；深度和身份有效
结果：计划绑定 request_id 和当前帧的 stable_id，再交控制器复核
```

如果两个弹夹在误差区间内几乎同样靠右，程序会把“唯一最右”判为不确定。若用户说“剩余”，答案必须结合 `MissionLedger.task_context()` 排除已经验证交付、保留中的和待验证释放对象。源码还存在一个单件“剩余”快速路径：指定 ID 在账本剩余集合且无保留时，可跳过多件完整性门；这是一项具体设计取舍，不能概括为“剩余指令总是要求全场景完整”。阅读 R3 失败时，要先确认走的是哪条分支。

## 第五章：回合驱动器与账本的状态含义

`EpisodeDriver` 是**流程协调者**，不直接求 IK。它的 `_prepare_observation()` 等控制器把篮区带到可观察状态；`_context()` 从新场景向账本要当前任务上下文；`_run_task()` 发请求、等待九格和控制器事件；`_cancel_and_wait()` 处理停止确认；`_read_only_closeout()` 在终止后只收证据、不再运动。`run_episode.RosTransport` 把这些调用翻译成 ROS 发布/订阅，并把事件写盘。

`MissionLedger` 解决“我抓到哪一个、前一条是否真的交付、剩余还有哪些”这些跨任务问题。它维护帧内 `id` 与稳定身份的对应、已交付集合、未确认释放集合、前序任务依赖、全局截止时间。`task_context()` 会检查场景新鲜度、身份是否确认、未知区、传感器问题、覆盖完整性和前序任务；`bind_plan()` 将计划中的目标绑定到账本；`record_event()` 按事件建立抓取、释放和放置证据；`summary()` 计算状态。没有这层，仅靠当前画面数物体，很容易把被遮挡的物体或已经抓走但尚未证实落带的物体再次选中。

一条任务可能处于以下不同结果，文字相似但含义不同：

| 事件/状态 | 能证明什么 | 还不能证明什么 |
|---|---|---|
| `plan_published` | 模型答案经语义校验且计划已发出 | 机械臂接单、抓到物体。 |
| `grasp_verified` | 本次抓取形成规定的接触/抬升证据 | 已经送上正确传送带。 |
| `placement_pending_verification` | 已释放、空爪回观察位，但落带证据尚不连续 | 交付成功。 |
| `placement_verified` | 本次释放与带上观测满足关联条件 | 独立赛事评分必然认可。 |
| `task_succeeded` | 驱动器核对账本中的交付证据后接受该任务 | 其他任务、整轮或官方评分均成功。 |
| `rejected` / `task_failed` | 当前任务未按目标完成；部分分支可安全了结 | 不能把“继续下一条”记为这条成功。 |

R3 代码允许计划接受前的语义拒绝走 `release_rejected_task()`，已绑定但未触碰目标的失败在实测停止后可走 `release_failed_task()`；二者均是“失败已了结、后续可尝试”的状态。若已有抓放证据而无法证明安全了结，继续执行被阻止。这里的失败继续机制提高了后续指令可执行性，也带来**计数口径风险**：后续“剩余”可能完成更多物体，`verified_objects` 较高，但被拒的那条指令仍失败。评估时必须同时读每条任务状态、整轮状态和独立评分，不可拿物体数替代指令成功率。

## 第六章：机械臂动作到底由谁决定

这里至少有四层决策。`controller.py` 规定动作**阶段**和顺序；`grasp_candidates.py`、`core.py` 给出可试的抓点、腕部姿态和标定补偿；`sim_with_feedback.py` 在当前关节状态下选实际**关节路线**；`trajectory_timing.py` 决定每个路线采样点**何时到达**。`planning_candidates.py` 提供 IK 种子、可行解和预览绑定检查，`joint_path.py`/`cartesian_path.py` 提供局部路径构造。所谓“动作策略在哪个函数”，应先说清问的是哪一层。

`Controller.select_grasp_pose()` 先重新绑定现时目标，调用 `generate_grasp_candidates()` 生成有限抓取候选；依次试常规竖直姿态、深度层、夹爪对称转向，常规耗尽后才试受限倾斜。`GraspAttemptHistory` 限制重复失败和预算。每个候选经 `core.calibrated_grasp()` 得到经过标定的抓取姿态，`preview_grasp()` 要求仿真侧证明从当前状态到接近、下降、抬升、搬运、放置存在一条守卫认可的完整路线。**候选通过预览才值得执行**；有限候选中“第一个可行”不等于全局最短或最顺。

`StableController.process_preview()` 从当前关节状态选有限 IK 分支，检查接近路线，以及同一工具姿态下的下降、抬升、搬运和放置。`plan_and_execute_trajectory()` 真正执行某段末端目标时，优先尝试绑定且起点仍吻合的预览路径；否则对于近距离目标尝试受守卫约束的关节直达、受守卫约束的笛卡尔连续路径，最后才尝试受守卫约束的 TRRT 回退。它还逐采样检查关节界限、台面间隙和持物姿态，重定时后再查一遍；报告 `planner_method`、规划耗时与诊断。预览只声明**采样关节/台面间隙/持物姿态**范围的有效性，源码明确说不构成完整网格、障碍物或自碰撞认证。

`Controller.execute_object_once()` 则把若干段运动和夹爪操作串起来：确认对象与抓点 → 接近/下降 → 闭爪和试抬 → 持物转运 → 对目标带选放置路线 → 下降/释放 → 退回观察位 → 验证。`move_held_linear()` 负责其中的持物直线分段意图；它向仿真侧反复提出末端目标，最终执行关节怎么走仍取决于当时的 IK 与路径守卫。释放前后还要持续看接触、空爪、画面和传送带，不是沿一个固定脚本播动作。

### 6.1 “向右放，却先向左动”的定位方法

“右”是**放置侧**，不是每个时刻末端或每个关节都朝右的约束。先向左可能出现在接近抓点、抬升避开篮壁、转出工作区、换 IK 解支、绕行放置目标等不同阶段；其中有些绕行合理，有些是可删的多余航点。不能只凭视频片段判断是哪一种。对同一 `request_id`，把 `grasp_candidate_set`、预览分支、`planner_method`、动作阶段、关节/TCP 诊断与 RGB-D 时间对齐，记录“左移从哪一段开始、对应末端目标是什么、与最近障碍的间隙如何”。若目标点本身先向左，检查 `execute_object_once()` 和 `move_held_linear()` 的分段；若目标向右而实际路径先向左，检查 `process_preview()`、IK 解支和 `plan_and_execute_trajectory()`；若路线正确只是顿挫，检查 `retime_path()` 与阶段等待。这样才能针对原因优化。

速度不能改时，流畅度仍受**路程长度、姿态连续性、停顿、规划切换次数和可达余量**影响。但少走路与避障、可靠抓取可能冲突。当前代码是受限候选和局部规划，不能证明对 B03 各场景乃至 B02 角度布局的全局最优；若要声称“所有动作最优”，须先定义指标（例如时长、关节总行程、TCP 行程、急停/失败率的权重）并在各登记场景独立测量。

## 第七章：抓到了和放到了，证据从哪里来

闭爪指令只说明“请求夹爪闭合”。`gripper_closure.ContactConfirmationWindow` 观察手指位置、受力、抓取传感器与时钟，要求连续窗口而不是单次跳变；`grasp_contact_monitor.py` 补充接触与试抬期间的受力证据；`lift_evidence.evaluate_lift_frame()`、`LiftEvidenceWindow` 用抬升后的深度图/接触来判断物体是否随夹爪离开。`controller.trial_lift_and_verify()` 把这些读数变成 `grasp_verified` 或空抓等结果。若外观上夹住却代码报空抓，先按证据层逐项查“没接触”“接触断续”“深度没看到物体上升”“相机/夹爪读数过期”，不要直接调抓取高度。

放置验证从 `release_id` 开始。`conveyor_observer.DepthConveyorTracker` 结合抓取、释放事件和深度带区观测，排除释放前已有物体，并尝试把带上新轨迹关联到本次释放；`core.verify_transport()` 看释放后连贯的带上运动，`verify_settled_placement()` 处理落点停稳的情况。若尚无连贯证明，控制器只在已释放、空爪且回观察位的条件下发 `placement_pending_verification`。停稳后的 `verify_pending_delivery_after_stop()` 是有时限的只读取证，不重新运动。这里的分层非常重要：**“抓走了”“爪子空了”“带上有同类物体”“本次这个物体落在正确带上”是四件不同的事。**

计分也要分层看。`episode/summary.json` 是程序自报的回合摘要；`supervisor_finished.json` 给记录器/停止等监督信息；独立场景评分还可能核对真实物体位置。任何一个单字段都不足以代替全部。尤其在服务器无法访问时，本导读只能解释判据，不能宣称当前服务器的任务通过率。

## 第八章：两条故障链的读法

**链 A：九格看对类别，但指令被拒。**从 `episode/events.jsonl` 找该 `request_id` 的 `infer_started`、`model_answer`、`validation_failed`；对照当时 `/tcei/candidates` 的 `class/id/stable_id/unknown_regions` 和 `task_context`。若候选类别正确，继续看 `semantics.validate_selection()` 对方位、数量、唯一性、身份和剩余集合的判定；若模型答案在推理期间变旧，还要看九格发布前的 `scene_unchanged()` 重绑定。不要把“模型分类正确”自动扩展成“语义计划应通过”。

**链 B：弹夹抓起后路线先左再右。**先用事件确认 `grasp_verified` 已发生，还是实际仍在接近/试抬；再对齐 `planner_method`、预览分支、各阶段末端目标、关节/TCP 诊断和视频。若是带物绕篮壁的必要间隙，删航点有碰撞风险；若是局部 IK 解支或预览缓存失效导致的大绕行，优化排序和绑定可能更有效；若路线短而动作不连续，查 `trajectory_timing.py` 的重定时及阶段等待。每个解释都须用同一回合的记录来证实。

以上是读日志的顺序，不是当前服务器故障归因。源码能告诉我们“可能在哪里”，具体一次失败仍要看对应版本的 `runtime_manifest.json`、画面和诊断。

## 第九章：场景先验、身份记忆与泛化边界

`perception_tracking.CandidateTracker` 不只是“给物体起编号”。它把当前检测与已有轨迹关联，对类别、像素距离、深度和遮挡进行检查；看见物体的一半时，`reliable_anchor_update()` 可阻止把身份锚点拖到残留半边。R3 的修补围绕一个实际工程问题：物体被抓走后，遮挡、残影或一次错误分类，可能在源区生成“同一个物体还在”的幻影轨迹。如果账本把幻影当剩余物体，后续指令就会选择错误目标或因集合不完整停住。因此读一次“剩余”失败，应同时看当前候选和 `source_lifecycle`，而不是只看框数。

`scene_layout_prior.json` 提供默认固定布局的类别/像素锚定信息。跟踪器有激活门：首轮扫描要命中足够多的先验位置才启用，随机布局原则上应不启用。这个先验能抑制固定场景里分类波动，但**位置接近先验不等于类别真值**；距离容差、物体密度和摄像机偏差会影响误激活风险。尤其 B03 是横平竖直而位置变化的登记场景，B02 又有角度和随机位置，不能把默认布局的成功直接外推给它们。当前本地代码的 `prior_tolerance` 为 30 像素；是否合适应以各场景实际布局距离和轨迹证据判断，不能孤立地称“30 像素安全”。

`CandidateTracker.reset()` 在新回合保留已经确立或已交付的轨迹，清理较年轻的未确认轨迹；`on_event()` 还消费 `grasp_verified/released/placement_verified` 等事件，推进对象生命周期。这解释了为何重启进程、换一轮任务或软复位不必得到完全相同的身份行为。**泛化检查的最小单元是“场景布局 + 启动状态 + 指令顺序 + 追踪历史”**，不能只拿单帧图片比较。

## 一次任务如何走完

1. `scripts/env.sh` 装入实例路径与 ROS 环境；`init` 写实例配置，`doctor` 检查依赖。`start` 通过 `launch_stack` 校验冻结文件哈希、独立目录和资源，必要时按登记的 case 摆位，四节点起动后 `probe_no_action` 核对无动作就绪。
2. 仿真发布 `/Jaka/camera/rgb`、`depth`、`camera_info` 等。`perception.py` 近时同步 RGB-D，检测物体区域、深度与朝向，`CandidateTracker` 保持身份，发布 `/tcei/candidates` 和 `/tcei/annotated_image`。默认九格检测通过 `/tcei/classify_request` 请求 `nine_node.py`，利用几何提案与模型分类结合。
3. `run_round.py` 拒绝重名/重复场景、进程失联、哈希不符、证据盘不足、夹爪非空载、相机过期及重叠执行；启动 RGB-D 和标量记录器，随后开启执行开关并创建 `run_episode.py`。控制台 B 只是这个入口的图形前端。
4. `EpisodeDriver` 为每条指令建立任务上下文、请求观测和规划。`nine_node.py` 用编号全图和候选列表选择对象；`semantics.py` 校验类别、方位、剩余物品和场景新鲜度，必要时由 `semantic_repair.py` 重问。校验失败是拒绝，不会把模型原文直接交给机械臂。
5. `controller.py` 重新绑定目标和现时观测，生成可抓姿态；经预览、工作区/支撑面/间隙/轨迹检查后，通过 ROS 命令驱动 `sim_with_feedback.py`。闭爪、试抬、接触、持物和传送带观测组成证据链；失败时按原因停止或恢复，不应仅凭“夹爪闭合”判成功。当前 `episode_driver.py` 对计划接受前的语义拒绝调用 `release_rejected_task`：账本确认未触碰目标时可继续下一条，若已有抓放证据或无法了结则停轮。
6. `mission_ledger.py` 记录任务、交付与待核验状态。回合写 `episode/events.jsonl`、`episode/summary.json`；监督器写 `supervisor_finished.json`。最终判断需要结合任务状态、物理落点、证据完整性和安全停止状态。`task_succeeded` 也不能代替独立赛事评分。

**B03 数据字段注意：**`make_scramble10.py` 的 v5 规则实际保持默认场景物体的平放姿态，必要时绕世界竖直轴旋转 90° 使长轴沿 X；但部分生成 case 仍保留模板中的 `randomization` 文字和 `yaw_delta_degrees` 字段，写着“均匀随机 yaw”。这两个元数据字段与实际写入的 `quaternion_wxyz/requested_quaternion_wxyz` 不一致。判断姿态应看实际四元数及启动后的物理真值，不能只看文字说明或旧 yaw 字段。这是当前数据可读性缺陷，不等于已验证实物姿态完全正确。

## 按现象反查程序位置

这一表与《v1 项目总览》的逻辑章节对应。先按现象找到责任层，再读该文件附近函数；不要从某个表面现象直接认定是大模型、控制器或仿真的单点故障。

| 现象或问题 | 第一检查位置 | 继续追查的位置 | 判断重点 |
|---|---|---|---|
| 物体漏检、类别混淆 | `perception.process_frame()`、`NineRotationDetector.detect()` | `source_components()`、`CandidateTracker.update()` | 是区域没提出、九格答错、关联错，还是旧类别锚点延续。 |
| “右下方/最右/剩余”选错 | `Nine.on_request()`、`semantics.validate_selection()` | `observation_readiness()`、`infer_validated_selection()`、`MissionLedger.task_context()` | 完整画面、候选关系、未知区和前序交付状态是否一致。 |
| 目标正确但抓取点偏 | `Controller.select_grasp_pose()` | `generate_grasp_candidates()`、`calibrated_grasp()`、`verify_approach_observation()` | 三维位置、主体几何、腕部方向、深度层和动作前复核。 |
| 抬起前出现反向移动 | `select_grasp_pose()`、`preview_grasp()` | `StableController.process_preview()`、`preview_move()` | 发生在接近分支还是预览生成的关节路线；该绕行是否为间隙约束所需。 |
| 持物后先向错误方向走 | `execute_object_once()`、`move_held_linear()` | `plan_and_execute_trajectory()`、`cartesian_candidate()`、`path_to_joint_goal()` | 传送带目标坐标、分段航点、IK 解支和替代放置候选。 |
| 路线正确但运动顿挫 | `trajectory_timing.parameterize_joint_path()`、`retime_path()` | `set_trajectory()`、`update_trajectory_tracking()`、`arrival_window.py` | 采样点间关节路程、速度/加速度限制、跟踪完成与阶段等待。 |
| 机械臂翻腕或走大弯 | `clearance_ik_candidates()`、`joint_line_candidate()` | `planning_candidates.evaluate_ik_solution()`、`guarded_joint_line()`、`continuation_path()` | 候选对当前关节姿态的距离、持物姿态约束与路径回退顺序。 |
| 夹爪闭合却抓空 | `close_gripper()`、`trial_lift_and_verify()` | `ContactConfirmationWindow`、`GraspContactMonitor`、`evaluate_lift_frame()` | 手指位置、受力、接触与试抬图像是否形成连续证据。 |
| 放下后显示成功但证据不足 | `verify_pending_delivery_after_stop()`、`MissionLedger.summary()` | `verify_transport()`、`verify_settled_placement()`、`DepthConveyorTracker.process()` | 释放身份、目标带轨迹、落点稳定和停止后的最终证据。 |
| 一轮突然停止或跳过任务 | `EpisodeDriver._run_task()`、`_cancel_and_wait()` | `release_rejected_task()`、`controlled_stop.py`、`supervisor_finished.json` | 是语义拒绝、预算不足、执行失败，还是停止证据未完成。 |

机械臂“动作策略”应按层理解：`controller.py` 定义抓放状态机和航点，`grasp_candidates.py` 与 `core.py` 定义抓取姿态，`sim_with_feedback.py` 选择并执行关节路径，`joint_path.py`/`cartesian_path.py` 生成路线，`trajectory_timing.py` 给路线分配时间。流畅度同时取决于路线形状和时间参数，不能只归因于速度设置。

## 读证据、定位问题的顺序

1. 栈目录 `launch.json`：场景、检测器、四节点命令、运行版本；`pids/` 与 `logs/`：节点是否活着。`case.json` 和 `scene_initialized.json` 只在指定布局栈出现。
2. 回合目录 `instructions.json`、`before_scene.json`、`runtime_manifest.json`：究竟执行了什么、入场观测是什么、用了哪份代码。
3. `episode/events.jsonl`、`summary.json`：按时间查语义拒绝、对象身份、抓取阶段、放置核验；再查 `supervisor_finished.json` 的证据完整性和停止状态。
4. `rgbd/`、`scalars/`、栈 `events/` 与各节点日志：把事件时间对到画面、深度、关节和夹爪反馈，区别“看错目标”“规划不可行”“抓空”“搬运掉落”“落带未证实”。

只看窗口画面或单个 `task_succeeded` 字段会漏掉错物体、错带、待验证放置和停止异常。B03 应优先逐场景核验官方式指令与横竖布局；B02 可单列扩展指标，不能与 B03 混算为赛事通过率。

## 学习顺序与边界

建议先读 `robot.sh → scripts/start.py → harness/launch_stack.py → scripts/run_round.py`，再沿 `perception.py → nine_classify.py → nine_node.py → semantics.py → episode_driver.py → controller.py → sim_with_feedback.py` 追一条任务，最后对照一次真实回合证据。先弄清谁发布、谁订阅、何时允许运动，再研究候选姿态和异常恢复。

本文此次仅核对本地 R3 源码，未进入当前服务器，也没有运行测试或现场动作。因此“可运行”“已完成抓取”“比赛最优路线”必须由对应服务器版本、场景和独立证据另行证明。
