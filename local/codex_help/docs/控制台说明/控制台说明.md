## 二、发射后的完整链路

```Plain Text
console → run_round → run_episode
```

控制台只负责"发射"；发射后 `run_round.py` 接管，检查链如下：

1. **run\_round 的准入检查**（任一不过即报错退出）：
回合名未用 \+ 无 `round_started.lock` → 四节点进程归属正常（`owned`）→ `warmup_complete.txt` 在 → `verify_resources`（含 BUILD\_MANIFEST 逐哈希）→ 数据盘 ≥8GiB → 执行开关均为 False（禁止重叠运行）→ **夹爪空载** \+ 8 关节反馈 → 候选新鲜（\<2s）

2. **建回合目录**：`RUNS/<回合名>/{pids,logs}` \+ `before_scene.json` \+ `instructions.json` \+ `runtime_manifest.json` \+ 栈上的 `round_started.lock` \+ `state/active_episode.json`

3. **起证据记录器**：`record_trial_rgbd.py`（rgbd/）\+ `record_scalar_evidence.py`（scalars/），就绪等待上限 **120s**（回合结束后仿真正在重载场景，1\~2 分钟，相机话题恢复需要时间）

4. **开执行开关**（`/tcei_controller/execute`、`/tcei_nine/execute` = True）→ spawn `run_episode.py`（`--instruction` 每条一个参数）

5. **supervisor 看护**：watchdog = budget\+60s；结束后读 summary、校验 `evidence_complete`（双记录器正常关闭）、停记录器、写 `supervisor_finished.json`、关执行开关；若 summary 报"运行中源码变化"→ 报错

6. EpisodeDriver 内部：见 Q2 的分支表；回合收尾自动 `_cancel_and_wait` \+ 测量停止

## 三、一回合几条的语义

- **五条全填 = 连打**：上条成功下条自动开始；`task_failed`（物理，带实测停止）会继续；**语义拒绝（rejected）必终止**

- **一次填一条 = 逐条**：被拒只废当条，复位后换下一条

## 四、操作卡

1. `bash robot.sh start <栈名>_$(date +%m%d%H%M) [--case ... --case-register ...]` → "已就绪"

2. `bash robot.sh console` → **核对/覆盖 5 条指令**（ 控制台不会按场景自动预填，预填永远是硬编码官方五条）

3. 生成指令文件 → 启动回合 → 盯状态区

4. 再跑一轮：回合间复位 → （按需改指令）→ 生成 → 启动

5. 修不好时：取消当前回合 → 复位；再不行按操作卡"万能恢复"

## 五、注意事项（源码级补充）

- 控制台**不校验栈状态**：它发射后靠 `run_round` 的准入检查兜底；栈没起好会在 run\_round 阶段报错（看 /tmp/\<回合名\>\.out）

- "summary 解析中…" = summary\.json 尚未写出，正常

- 重复"生成"在**同一分钟内**会同名覆盖（`%d%H%M` 精确到分）；不同分钟的文件并存，属正常，垃圾文件可留可清

- 复位脚本要求 `/tcei/stop_ack` 4s 内有消息——sim 没起或已死时该步超时跳过（打印 latch 异常），但 controller 重启与清锁照做

- 自定义指令：任意"抓取\<方位\>\<物品\>，放到\<侧\>传送带"句式都支持；**象限词（左上/右上/左下/右下）\+ 极值（最左/最右）\+ 唯一类别 \+ 剩余**为已验证语法；"最X方"会触发 EXTREME 完整性门（有被未知碎片误杀的风险，见《失败分析》）

## 〇、四个问题的直接回答

### Q1：打开控制台时，它能读到已开启的栈吗？场景配套指令是读到的吗？

**栈：不读。指令：也不是读的，是硬编码——"读到"是巧合。**

- 打开窗口时，5 个输入框预填的是**源码里写死的官方五条**（`examples` 数组，L90\-92）。控制台**不读** `active_stack.json`、**不读**栈目录里的 `case.json`，对"当前栈是什么场景"完全无感知

- 你看到"配套指令出现"，是因为 **B02 的 30 个场景指令组合数 = 1**（全部场景共用官方五条）——硬编码预填恰好就是你场景的配套指令

- **推论（对 B03 重要）**：将来 `cases_scramble10/` 的 10 个场景指令各不相同，打开控制台时**不会自动预填**，必须手动覆盖 5 条（你之前"我重新写入覆盖"的做法是对的）

- 控制台唯一一次读栈：**回合间复位脚本**里读 `active_stack.json` 取 `stack_dir`（见 Q3）

### Q2：启动回合后，是不是从第 1 条到第 5 条顺序执行？

**是。同一回合内顺序执行，共用一个预算（console 不传 ****`--budget`****，run\_round 默认 600s）。**

`EpisodeDriver._run_task` 逐条处理，分支语义（`episode_driver.py`）：

|上一条结果|行为|
|---|---|
|`task_succeeded`|直接开始下一条（无需复位）|
|`task_pending_verification`|记账后开始下一条|
|`task_failed`（物理失败）|要求**实测停止证明**；失败任务释放成功 → 记 `task_failed_continuing` → **继续下一条**；未释放 → 终止|
|**`rejected`**** / ****`plan_rejected`**** 等语义拒绝**|**直接 ****`EpisodeFailure`**** → 整回合终止**（`:295-297`），发 cancel \+ 测量停止，summary 状态 `stopped`|

> 这就是"连打形态：任何一条被拒 → 剩余不跑"的源码出处。语义拒绝没有重试机会（`semantic_repair` 的 3 次重答是在被拒**之前**发生的，重答仍被拒才算 rejected）。

### Q3：「回合间复位」是做什么的？逻辑是什么？

按钮执行 `RESET_SCRIPT`（写在 `/tmp/entryb_reset.py`，在 `env.sh` 环境下运行），**三步**：

1. **停止锁存复位**：等 `/tcei/stop_ack`（4s 超时）→ 取 stop id → 向 `/tcei/stop_reset` 发复位 → 清掉 sim 侧的"测量停止"锁存

2. **重启 controller**：`pkill controller.py` → sleep 2 → 按 launch\_stack 同款参数重启（`_execute:=false` 等）→ 把新进程的 `pid/pgid/start_ticks` **回写 ****`pids/controller.json`**（进程守卫靠它认进程）

    - 为什么必须重启：controller 的 `cancelled` 锁存**没有清除路径**，重启是规定动作（源码注释原话）

3. **清回合锁**：删 `<栈目录>/round_started.lock`——这是 `run_round.py:29` 的回合锁，不清掉下一轮会报"本轮名称已使用，或当前场景已运行"

### Q4：我的操作步骤"生成指令文件 → 开启回合"对吗？

**对，而且顺序是强制的**：`on_launch` 先检查 `instr_file` 存在，没有就提示"请先点击「生成指令文件」"。

- **生成**：收集非空输入框 → 写 `RUNS/manual_<日时分>.json`（JSON 数组，`%d%H%M`，10/4 起从时分秒改为日时分，避免跨天撞名）→ 回合名 = 文件名 = `manual_<日时分>`；**同一分钟内重复点击 → 同名覆盖**；留空的行不执行（"留空即只执行填了的"）

- **启动**：`cd ROOT && setsid nohup bash robot.sh run manual_<日时分> --instructions <文件> > /tmp/<回合名>.out 2>&1 &`（脱离会话后台跑，终端日志在 /tmp）
