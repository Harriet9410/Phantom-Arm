## 2. 修改在哪里、为什么

### `nine_classify.py::_classify_proposals()` / `_scan_worker()` / `detect()`

- GT（手雷/手电筒）复核先执行；若它把 Torch 改成 Grenade，随后会做 GS（手雷/烟雾弹）复核，补上旧顺序漏掉的烟雾弹辨别路径。
- 四选一终审必须与复核后的当前类别一致，或被两个裁剪答案共同支持。否则记为 `unresolved_conflict`，而不是独自改写类别。终审缺失或两次不一致也记未决。
- 有旧记忆的未决物体保留最后接受的类别，按本次实际几何刷新“看见物体”的时刻；清除 pending 改判，不刷新鉴定时刻、有效期或完整扫描证明。首次识别就未决的物体不建立已知类别，仍为 unknown。这里并没有保证旧类别正确，只避免用自相矛盾的新扫描推翻它；初次错误仍需要后续有一致证据的扫描纠正。
- `class_support_scan_ids` 只保留最多两次真正完整、已接受的扫描 ID；廉价全图同意、缓存重复帧和未决扫描都不增加它。九格两轮确认新类别时，记录 pending 那一轮和确认这一轮，因此跟踪器可立即复用这份证据，避免额外再等待两次完整重扫。
- 新增 `nine scan started`、未决原因、存储类别支持扫描 ID；未决也保存冲突图片。原有速度、缓存间隔和第五项等待时长没有调整。

### `perception_tracking.py::CandidateTracker.update()`

- 替代类别按不同的完整支持扫描 ID 计票；重复同一缓存一百帧仍只算一份。几何必须唯一关联且通过现有遮挡/锚定检查。
- 两次有效扫描才改判；未知类、未决扫描、遮挡不构成授权。后续确有两次新证据时允许再次纠错，不以运行时未知的“错→对方向”做判断。
- 改判审计绑定 `protocol=tracker.class_recheck.v1`、稳定 ID、前后类别、帧号、两扫描 ID。它和 `recheck_majority` 在后续候选中持续携带，避免账本错过发生改判的那一帧。

### `mission_ledger.py::_validated_reclassification()` / `task_context()`

账本不再只凭来源字符串接受类别变化，而是检查上述审计与当前稳定身份、账本旧类别、候选新类别、帧顺序和两次不同扫描是否匹配。缺证明、重复扫描、错身份或未来帧仍报 `stable_identity_class_changed`。审计的扫描 ID 可回连感知日志；它是受信任感知进程的证明，不是模型分类正确的保证。

`perception.py` 和 `episode_driver.py` 增补证明字段、分类状态；lineage 同时直接记录 `layout_prior_active`，DS 不必再仅靠位置推断。双清单同步更新，机械臂动作与速度未改，本轮不声称修复 s01 掉件。

## 3. DS 按顺序执行，不需再等 Codex 授权测试

### A｜先检查候选，再部署（失败则停止并报告）

1. 在本地候选目录先运行下列脚本，或在服务器备份并部署后运行。脚本只使用标准库、真实分类方法的 AST 和实际 tracker/ledger 模块，模拟标签以验证裁决和证明规则；不加载模型、不启动 ROS、不驱动机器人。它不能替代真实分类或仿真成绩。

   ```text
   python3 R7-1b-DS代码检查.py --code <R7目录>/_r71b_files/tcei_stack
   ```

   同时由 DS 对五个修改后的 Python 文件做语法检查。检查覆盖：终审冲突、GS 复核顺序、未决记忆与 pending 中断、首次未知、廉价扫描不冒充完整扫描、缓存重复帧不能改判、两扫描改判及二次纠错、改判来源后续保留、遮挡守卫、伪造/不匹配审计拒绝。
2. 服务器代码根目录按上轮报告为 `/root/tcei_final_v2_23/tcei_260920v2`。逐一核对 JSON 的 **before** 七项 SHA；任何不一致，停止覆盖，报告实际路径和 SHA。确认无在跑的任务，备份这七个旧文件与 SHA 到独立回退目录。
3. 推荐按 `_r71b_files/` 相对路径逐文件交付；也可应用补丁，但必须验证每项 **after** SHA，不以 `git apply --check` 返回码替代。上传时保持字节和换行；本地 `arm/` 前缀对应服务器代码根，不应额外套一层 `arm/`。
4. DS 执行服务器 `scripts/verify_package.py`，双版本一致、清单无 mismatch 才继续。记录服务器真实 HEAD 与工作树；候选安装与检查完成后作为一个阶段提交，排除 `state/active_*`、运行输出和临时脚本。R6 已存在的 `harness/launch_stack.py` 改动需纳入冻结版本，并与当前 PACKAGE SHA 对齐，不可丢失。

### B｜先跑最小定向集合

**一次版本冻结，中途不改代码、清单、模型或类别表。** DS 执行 s02、s04 各一轮，再执行 s03 和 s01；每案记录五条任务各自的 started/succeeded/rejected/failed、实物核验、人工干预和首个失败。前两案不再漂移且能五条闭环、后两案无阻断后，再各复跑一次 s02/s04。

重点核对：

- s02/s04 的目标物体是否仍产生矛盾的 final；矛盾时必须记未决，不能偷偷换成另一个错误类别。旧类别保留与 unknown 必须如实报告；第一次识别可能就错，不能只看有没有 `confirmed_reclass`。
- 每次 tracker 改判的两 ID，能否在同一物体的九格完整扫描中找到；`stable_id` 是否一致，后续帧是否持续带审计。
- s04 第三条“类别不唯一”的拒单是否消失；第五条是否实际发起并核验成功，不能只把等待结束算成功。
- s01 掉件、s03 数量/类别拒单是否仍存在。这些若未修复，立即返回原始结果，不宣称仅分类修复就已完成 V0。
- `layout_prior_active` 在 B03 是否为 false；报告真实值，不用固定布局表或场景真值“纠正”运行标签。

任何检查失败、误抓、错投侧或新安全异常，停止升级，保存首个失败的分类回答、audit、lineage、episode 与图像。普通定向失败后不要反复重跑挑成功的一次，也不要擅自换阈值；交给 Codex 做下一处修复。

### C｜定向达门后直接跑封版验收

第一批达门后再同版复跑十案，报告每案首次/复跑成绩、失败类别和总时长。两批各五十条是验证样本，不是机器人应读取的题库，且不足以估计真实随机世界的成功概率。B02 斜放三十案、重构、文件重命名和实机均在 V0 后。
