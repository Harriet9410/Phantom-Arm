## 三、决定性发现：漂移是**两层**的，当前绑定约束在**跟踪器层**

### 3.1 审计路径（九格存储层，v0 下实测）
**s02 @(672,350)（B03 真值：Smokegrenade）**
```
new Smoke → same Smoke → pending Torch → confirmed_reclass Torch → same Torch ×2
→ pending Smoke ×2（想回退但被挡：pending 覆写）
```
**s04 @(672,350)**
```
new Smoke → pending Torch → same Smoke → pending Torch → confirmed_reclass Torch
→ pending Grenade → confirmed_reclass Smokegrenade → same Smokegrenade   ← 九格自行纠正回正确类别
```

### 3.2 层间不一致（决定性证据）
| 案 | 九格存储层序列 | **发布层序列**（events 中 obj-0003 的 class） |
|---|---|---|
| s02 | Smokegrenade → **Torch** | **Torch** |
| s04 | Smokegrenade → Torch → **Smokegrenade（已纠正）** | **Torch**（从未回到 Smoke） |

**事实**：s04 的九格已把该物体恢复为正确的 Smokegrenade，但发布出去的候选**始终是 Torch**。
**推断（强）**：发布层类别被**跟踪器锚定**压住——`perception_tracking.update()` 对已确立轨迹执行 `c['class']=prior['class']`（`established_track` 覆写），而 F1a 的改判是**每轨迹一次上限**（`alt_reclass_done`），因此一旦锚定被错误改判为 Torch，**再也无法回正**，即使九格自己已经纠正。
**替代解释及排除**：不能由"九格又错了"解释（s04 审计末态 stored=Smokegrenade）；也不能由"未发起 t5 与类别无关"解释（两案 remaining 均只剩 `obj-0003` 且阻断原因就是 `stable_identity_class_changed`）。

### 3.3 与 Codex 假说的关系
Codex R6 消除了"要求按编号回答却没有编号图"的输入矛盾——**这一步确实改善了上游**（证据：s04 的九格在 v0 下能自行纠正回 Smokegrenade，R5 时未观察到）。但**阻断点已下移到跟踪器/账本层**，故单看 s02/s04 的最终成绩无变化。

## 四、给 Codex 的 P1 建议（本报告不实施）

基于 §3 证据，最小修复点应在**跟踪器层的类别锚定**，而非九格：
1. **允许回正**：当前"每轨迹一次改判"使错误改判不可逆。建议改判配额改为**方向性**（错误→正确方向的纠正不限次，或允许在九格给出 `confirmed_reclass` 级证据时回正），并保留 `reclass_audit`；
2. **以九格审计为准**：当九格存储类别（含其两轮门与 `scan_id` 审计）与跟踪器锚定冲突时，宜信任九格而非锚定——因为九格有可审计的两轮门 + 冲突图像，锚定只有"历史类别"；
3. **账本跟随需绑定受审计改判**（Codex R5 已提）：`class_source='recheck_majority'` 仅是一个字符串，应改为校验稳定的 `reclass_audit` 记录；
4. **保留** `stable_identity_class_changed` 阻断与类别拒单，不放松。
5. 另建议修 `_ds_r5_matrix.py` 的审计日志路径（`_stack/logs/perception.log`，DS 已修本地副本）。
