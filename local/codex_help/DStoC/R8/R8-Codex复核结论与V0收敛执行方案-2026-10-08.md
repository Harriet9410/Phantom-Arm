# R8｜服务器复核结论与 V0 收敛执行方案

> **Codex 撰写｜2026-10-08**  
> 本文是下一阶段的实施依据。本次只读服务器源码、已有日志、场景和物理真值，未修改服务器，未运行模型、检查脚本或仿真。本文中的“改动”“验收”均为待执行事项。代码推进按实质阶段提交；测试交给 DS。后续交付进入本 R8，注明 DS 或 Codex 撰写。

## 1. 负责人判断：为什么一直到不了 V0

**当前有可运行的系统和可回退的候选，但还没有稳定 V0。不能把 R7-1b 直接封为参赛版。**

问题已经能落到具体代码。此前我们多次围绕类别漂移增加保护、记忆和审计，但没有先验证“图像输入→模型回答→答案解析→类别裁决”能否可靠输出类别。错误被挡住后变成 unknown，unknown 又被全场等待放大为整轮超时。同时，验收目标表存在错误，使部分正确动作被判失败，进一步干扰了判断。

我上一轮将主要问题概括为“上游模型错认”，仍然过粗。本次发现有些正确的类别结论已经出现在模型回答中，却被答案解析和后续裁决丢弃。模型也确实会答错，两种情况必须分别处理。R7-1b 是未达目标的候选，我不把新增日志和保护机制等同于成功率改善。

R8 的优先顺序：

1. 修正验收口径，用已有记录建立可信基线。
2. 收敛分类的输出协议与裁决，用保存图像先验证，不急着整轮仿真。
3. 合并重复等待，按指令处理 unknown；必须同步补齐未知区域语义，不能直接删保护门。
4. DS 完成定向及同版完整验收，通过后立即冻结、封装。重构和新功能放到克隆实例。

## 3. 已定位的问题及证据

### F1｜正确回答会被全文关键词解析丢弃

位置：tcei_stack/nine_classify.py 的 _parse_class_answer()、_recheck_agree()、_classify_proposals()。

可复核案例：s01，扫描 **9b0d586878**，p3，像素约 (671.5,349.5)，该场景中的烟雾弹。

| 阶段 | 原始回答 / 处理结果 |
|---|---|
| crop_en、crop_zh | 均为 Grenade，错误 |
| recheck_gt 两次 | 均回答手雷，错误 |
| recheck_gs 两次 | 均先回答“这个物体是烟雾弹（Smokegrenade）”，解释中又出现“手雷通常呈小型椭球体” |
| 当前解析规则 | 全文检出两类；比较句不属于当前否定规则，因此无法得到唯一类别，专项复核未更新原类别 |
| final 两次 | 均回答 Smokegrenade（烟雾弹） |
| 最终 scan audit | pre_final=Grenade，final=Smokegrenade，crop_votes=[Grenade,Grenade]，判 final_conflict，stored_class=null |

这是“模型给出过正确结论，但程序未能采用”的明确案例。根据源码可还原这条路径，scan audit 与之吻合；本次没有运行解析器测试。

不能据此改成“全文取第一个类名”，因为其他回答确实自相矛盾。应修正输出协议和裁决方式，让机器读取明确的类别结果。

### F2｜全图双票、排他二选一及终审形成了相互放大的错误

可复核案例：s04，扫描 **a270e75518**，p3，实际烟雾弹。

1. 全图给 Torch，被代码计为两票；两个裁剪给 Grenade。平票采用全图，得到 Torch。
2. GT 复核先说手雷，解释又提到军用手电筒；全文解析无法唯一归类，原 Torch 留下。
3. GS 只处理 Grenade/Smokegrenade，所以该物体没有进入烟雾弹复核。
4. final 两次也回答 Torch，与现有 Torch 一致，被接纳为新类别。

因此，仅交换 GT/GS 顺序并没有解决问题。二选一可能排除真实类别；把一个全图回答重复算两票也没有增加视觉信息。后续“终审与前序一致”仍可能一致地错。

**拟定方向：分类统一使用完整类别集合；取消强制二选一的覆盖权，不再把同一全图回答复制为两份证据。新的裁决必须先经过保存图像验证，不能凭这个方向就宣称准确率已提升。**

### F3｜重复推理与串联等待吞掉比赛时间

直接统计现存 nine_events.jsonl，按同一 tag 下恰好两次的 recheck/final 回答配对：

| 案例 | classify_answered 数 | 可配对组 | 两次原文完全相同 | 超过 100 字符的回答 |
|---|---:|---:|---:|---:|
| s01 | 200 | 62 | 62 | 60 |
| s04 | 150 | 47 | 47 | 44 |

这些数字仅描述两次运行，不是准确率统计。现装分类服务 sampling=false；同图同提示的重复调用，在这些日志中没有提供不同回答，仍实际消耗推理时间。max_new_tokens=400 允许长篇解释；该值同时用于分类与任务选择，修改时要按用途区分。

s01 首次扫描从 1791459610.889981 到 1791459742.353296，约 **131.46 秒**，这是扫描墙钟跨度，包含启动期间等待，不能全部算成 GPU 推理耗时。s04 首次、第二次扫描分别约 **81.10 秒、67.13 秒**。

nine_node.py::run() 先最多等 label_wait_seconds=90，再调用 wait_for_observation()，后者从调用时刻重新分配 observation_wait_seconds=130。s01 前两条实际各约 **220.17、220.20 秒**后拒绝，第三条又等约 151.49 秒直至全局超时。问题不是机械臂速度太慢，而是任务尚未开始就耗掉了预算。

### F4｜unknown 语义没有贯通，不能直接删除全场等待

nine_classify.py::detect() 会发布 class=unknown、confidence=0.90 的候选。其分类失败分支检查 class is None，却没有将字符串 unknown 同等处理，因而未知类别未必进入 unknown_regions。recognized_count 当前也可能把 unknown 算进去。

semantics.py::_unknown_may_affect() 又存在两条需要联动核查的路径：

- 若 region.class 是字符串 unknown，当前“已测类别不同于目标”的判断可能把它排除。
- unknown 区域如果与它自身的候选框重合，通用包含关系豁免可能把它当碎片排除。

现有 nine_node.py 全场 unknown 等待挡住了部分上述问题，但也把无关区域的未知物体变成全局阻断。**删除等待而不修 unknown 表达，会造成错误放行。**

### F5｜场景期待目标表从模板继承，没随指令更新

直接核实服务器十案：expected_object_ids 全是同一数组：

~~~text
[smoke_bomb, Magazines, Flashlight, hand_grenade, smoke_bomb_01]
~~~

make_scramble10.py::main() 深拷贝模板后改了 instructions 和 expected_sides，却未同步重建 expected_object_ids。run_registered_batch.py::audit() 又按任务序号使用该数组。

例如 s04 第一条抓手雷，实际 hand_grenade 正确，验收却期待 smoke_bomb；s03 第三条抓烟雾弹，实际 smoke_bomb 正确，验收却期待 Flashlight。这些 false 不能当成机械臂失败。

### F6｜原报告还存在跨场景真值和计数错误

- s03 的 p3 不是烟雾弹。该次冻结 case.json、ground_truth.jsonl 首帧及 1a81b4d6b1_numbered.jpg 相互支持：中下方为 hand_grenade，初始 Grenade 正确，后续 Torch 错误。不能把 R6/s02 相近像素位置的烟雾弹真值沿用到 s03。
- s03 的 8 条 reclass_audit 记录仅有 **1 个不同审计**：stable_id=71217290-obj-0003，frame=2778，Grenade→Torch，扫描 ab7941d5c4、8ab55d1f18。不是连续改判八次。
- 无 stable_identity_class_changed 事件，只能说明未记录这种阻断；不能单凭事件数为零就证明每个任务都实际走过并通过账本改判分支。
- s01 的中下方烟雾弹在所读扫描中持续未建立类别；不能概括为“四案都把同一处烟雾弹建立为 Torch”。

这些纠正不改变“当前不能封 V0”的结论，但会改变修复优先级。

## 4. R8 执行顺序与具体修改要求

### 阶段 A｜先让验收可信，不重跑机器人

修改位置：test_tools/make_scramble10.py::main()/assert_instructions_satisfiable()、test_tools/run_registered_batch.py::audit()、cases_scramble10 的期待目标元数据及登记清单。

**A1. 修正生成器和十案期待顺序。** 依据各案指令与物体布置生成期待目标，不继承模板顺序。当前冻结十案、前面任务全部按要求完成时，正常顺序如下。表只用于离线验收，不得进入运行时识别或选物逻辑。

缩写：S=smoke_bomb，S2=smoke_bomb_01，M=Magazines，T=Flashlight，G=hand_grenade。

| 案例 | 正常五条目标顺序 |

| s02 | S、M、T、G、S2 |
| s03 | M、T、S、G、S2 |

| s05 | T、M、S、G、S2 |

DS 实施时根据同版场景独立核对上述表与 expected_sides。固定现有摆放和姿态，不为了修验收重新采样场景；登记新的文件 SHA，并分别比较修改前后的物体姿态、指令、预算，确认这些字段一致。保留旧批次原始 case、campaign 和结果，新评价写独立文件，注明原批次 SHA、评价程序提交和规则版本。

**A2. “剩余”按任务启动时的剩余集合验收。** 第五条可能包含多件，不能只期待一个 object_id。依据该时刻物理真值和此前已独立确认的交付构造集合，实际交付不能重复、漏件或错侧。此前指定类别任务被拒，后续把物体作为“剩余”搬走，也不能补记前面指令成功。落地规则需区分篮内物体、已释放待确认物体和丢失物体，不能将看不见当成交付。

**A3. 分类正确性与物理交付分别保留。** 当前 audit() 只有 actual_class==event.category 才采集传送带样本，使 s02 第五条“错标签但可能已正确搬走”没有物理样本。修改为先独立核实物体身份、去向与持续在带，再单列模型类别是否正确、是否满足当前指令。不要以“剩余不要求类别”为由把错标签洗成正确识别；也不要仅凭错标签断言物体没有上带。

原始物理真值仍在服务器，优先离线重算 R7 两批，**无需重新仿真**。该重算和必要检查由 DS 执行。

阶段完成标准：s03 第三条、s04 第一/四条不再因错误期待顺序误判；“剩余两件”能按集合核验；s02 第五条分别给出物理、指令、分类结果；旧证据保持原样。作为一个阶段提交。

### 阶段 B｜用保存图像确定分类方案，然后才接入运行

修改重点：nine_classify.py::_ask()/_classify_view_crop()/_parse_class_answer()/_classify_proposals()，nine_node.py::on_classify_request()。继续使用当前一个模型进程和现有请求通道，不另起模型副本。

**B1. 候选输出协议。** 分类请求增加明确用途，例如 purpose=object_classification。该用途使用短输出预算，先以 max_new_tokens=32 作为待验证初值；要求单个结构化字段，如 {"class":"Smokegrenade"}，允许 unknown。任务规划输出仍保留原配置，不能全局从 400 改成 32。

读取完整结构化结果并校验类别；无法解析、截断、缺字段或输出多结论均视为协议失败。最多一次格式修复，失败继续 unknown。不要用“截取第一个英文单词/第一行类名”绕过歧义。32 不是已验证性能最优值，DS 根据格式完整率决定一次调整并冻结。

**B2. 先验证更短的分类链。** 移除同图同提示的两次一致投票、GT/GS 强制二选一覆盖和全图复制双票。首选试验路径：

1. 对同一深度提案取得目标居中的原图裁剪，保留有限上下文；不从画过编号和框的图上再裁剪。
2. 使用统一完整类别集合和结构化短回答；类别声明与请求选项一致，不能声明支持压缩干粮却在分类问题中永远排除它。本轮现有场景的四类必须先通过，尚未验证的类别如实标注能力范围。
3. 核查阶段增加一份真正不同的视觉输入作比较，例如同一物体不同边距的裁剪。必须记录输入哈希和边距，不能换一个扫描 ID 就算新视觉证据。单纯放大不会恢复原图没有的细节。
4. 两视图一致才建立本候选类别；不一致保持 unknown。第一次 wrong-but-consistent 仍是必须统计的错误，不能用审计完整掩盖。

这是待验证候选，不是已证实解法。旧 final 提示曾正确识别 s01 烟雾弹，也曾错认 s04 烟雾弹，因此不能直接把“永远信 final”作为新规则。旧全图输出可先保留在离线对照，不再给它未经验证的加权覆盖权。

**B3. 明确图像与请求绑定。** 每个用于验收的回答至少有 request_id、scan_id、同次提案几何、原图/裁剪输入哈希、原始输出、解析类别、采用/拒绝原因、用途与输出预算。优先复用现有日志，仅补缺失字段。跨扫描按几何和稳定身份关联，禁止沿用 proposal_index 或像素真值标签。

**B4. DS 先做离线小集合，再决定是否替换运行分类。**

- 使用 R7 已保存的 s01/s02/s03/s04 原图，覆盖四类、两枚烟雾弹、首次识别与后续冲突。按实际实例标注类别；真值只在评价端使用。
- 每案先取两个有不同时间/画面状态的五物体快照，目标约 40 个实例；若某案没有两份合适快照，实际数量如实写，不用完全相同图片填数。
- 先按运行/场景划分调试与留出组，同一原图的两种裁剪必须归入同组。留出组第一次评价失败后不能改提示再称它为未见样本。
- 报告正确已知、错误已知、unknown、协议失败四项及完整混淆矩阵；另报请求数和总耗时。禁止只在“已识别物体”分母上计算准确率，忽略大量 unknown。
- 必看反例：s01 p3 的正确烟雾弹答案是否仍被程序丢弃；s04 p3 是否仍被当 Torch；s03 p3 的手雷能否保留；s01 右下弹夹与左下手电筒是否正确区分。
- 接入仿真的小集合门：留出组全部实例分类正确，协议完整，不再把已知四类长期留为 unknown；相同实例支持两视图一致也必须与标注一致。小集合通过不等于普适性通过，后面仍要完整场景验收。

如果短协议和裁剪调整后仍出现**一致的错答案**，或仅靠大量 unknown 才没有错答案，停止继续堆裁决规则。当天交回失败图、模型实际加载来源和原始回答，由 Codex 决定针对当前分类输入做小规模适配训练，或评估已有模型能力。不要先跑十场景碰运气；不要自动换模型、打开定位适配器或启用真值布局表。

阶段完成标准：协议和候选路径在保存图像上得到真实结果，模型/提示/裁剪配置冻结。离线通过才接入运行；保留按真实完整识别结果生成的 R7 身份审计，廉价缓存不新增完整识别证明。作为一个阶段提交。

### 阶段 C｜合并等待，并让 unknown 只阻断它实际影响的选择

涉及 nine_node.py::run()/wait_for_observation()，perception.py 的跟踪后候选发布，nine_classify.py 的类别统计，semantics.py::observation_readiness()/_unknown_may_affect()/validate_selection()。

**C1. 只保留一个绝对观测截止时刻。** 在请求开始时计算 min(started+observation_wait_seconds, global_deadline)，标签等待、图像配对和身份确认共享它。分类补扫与观测配对并行等待，不先消耗 90 秒再重新计 130 秒。首版沿用现有 130 秒上限作为唯一上限，先不通过加大预算解决；分类收敛后再依据耗时审视是否需要缩短。该更改只防重复计时，不保证 unknown 自动消失。

**C2. 先补齐未知类别的发布语义。** 保留 unknown 候选及身份以维持跟踪、图像编号，但不要计入已识别数量。对真实物体的未分类区域补充明确原因 unclassified_real_object、当前 bbox/pixel 与位置时效，进入对外 unknown_regions，使完整性字段真实反映未分类状态。

建议在 perception.py 完成 CandidateTracker.update() 后、组装发布场景前加入这类“语义未知区域”，避免把物体自身的分类未知框当成几何遮挡传回 tracker；否则 reliable_anchor_update() 可能因框与自身重叠，永远拒绝建立/更新锚。原有真实遮挡仍按现有路径进入 tracker。

**C3. 修正 unknown 的排除条件。** _unknown_may_affect() 只有被接受的已知类别才能触发“类别不同”排除；字符串 unknown 不能。对于 unclassified_real_object，不可使用“被自身候选包含”或仅按面积较小的碎片豁免。真正深度碎片保持原有受限处理。跨场景历史位置、遮挡后失踪位置不能作为当前区域的排除依据。

**C4. 用同一个任务相关性判定贯穿入口与最终校验。**

- “左上方的弹夹”：若已知目标可靠，unknown 的完整当前包围框连同误差界完全在左上区域之外，可以不为那个 unknown 等待；边界相交仍等待。
- 同区域 unknown、没有区域限制的唯一目标、需要比较全场的最左/最右，以及“剩余/全部”，首版保持保守，不能证明无关时继续阻断。
- 模型仍负责根据图像和原始指令选 ID；相关性判断只决定是否具备安全解释条件，不按场景答案代选目标。
- 同一 helper 用于前置等待和最终 validate_selection，避免入口放行、后置仍按另一个规则阻断。未知候选不得作为抓取目标；相机新鲜度、图像绑定、身份确认和抓点可靠性检查保留。

**C5. 检查“剩余单选快速路径”。** semantics.py 当前在 len(ids)==1 且 ID 在 remaining_ids、无 reserved 时提前返回。放松 unknown 等待后，不得让该路径绕过完整性和前序依赖。快路径至少仍需证明剩余集合完整且确实只有这一件；上文的修复必须覆盖此处。

DS 必须验证：外区域 unknown 不再拖住无关区域指令；区域内 unknown、失踪物体、剩余集合不完整仍拒绝；同一 unknown 不再经历 90+130 双重等待；unknown 自身不会破坏 tracker 锚。作为一个阶段提交。

## 5. 进入 V0 的验收与封装

所有执行由 DS 完成。按 A→B→C→定向→完整验收推进，前一阶段失败即回交证据，不反复重跑挑最好一次。

1. **已有记录重算**：阶段 A 后先拿到可信 R7 基线，不要求新仿真。
2. **离线分类门**：阶段 B 通过；同时覆盖解析失败与真实错认，不能只跑 mock 标签测试。
3. **候选检查**：确认代码、模型/适配器来源、提示与配置版本、双清单；检查 B/C 的反例。Codex 不代跑。
4. **定向四案**：先 s01、s03，再 s02、s04。前两个正是当前零动作和多拒单场景。若失败，交首个原因与原始图像/回答，不先进入完整批次。
5. **同版验收**：四案通过后，官方完整五条 + B03 十案一批；无系统性阻断后再同版十案复跑。模型、运行代码、阈值、中途人工干预都要记录；改版后不能拼接不同版成绩。
6. **冻结包**：保留一个源提交、双清单、模型和环境索引、启动/运行/停止说明、已知限制、验收索引、回退步骤。发布包清理运行时 active 状态和开发证据引用，原始证据继续归档；不要边封装边重命名或改行为。

V0 的内部放行标准仍是：五条指令各自闭环，目标/数量/去向正确，独立物理交付得到确认，预算内完成，无反复出现的分类阻断、错抓、错投或掉件。候选已经有错标签时，不因“剩余物品恰好也该搬走”就忽略它。

若分类修复后暴露掉件或动作问题，单独定位具体动作段再修，不预先重写全部机械臂策略。本轮现有失败大多发生在任务执行前；零动作没有证明机械臂抓取稳定，也没有证明它不稳定。

这套门是项目内部的有限样本验收，不能替代官方规则，也不能证明真实世界随机摆放的普适成功率。本次未重新检索比赛规则，不新增“官方规定必须如此”的说法。

## 6. 预计还差多少工作，怎样避免 R9/R10 无休止循环

当前差的是“可靠分类、有限等待、可信评价”三个闭环；封装文件不是主要障碍。不能再用新增日志数量、补丁数量或单次满分来描述接近 V0 的程度。

工程安排估计：阶段 A 和阶段 B 的第一轮离线判断应集中在半天到一天内完成，这是人员投入估计，不是已测工时。阶段 B 若通过，B/C 接入、定向、完整验收与封装再预留约 1–2 个工作日；这是条件估计，不能承诺届时一定封版。若 B 的留出图仍持续错分，当天就做模型路线决策，训练工期另估，不继续保证“一两处小修就结束”。

定向四案上一轮仅任务运行时间合计约 37.6 分钟，另有启动/停止开销。官方一轮加两批十案共 21 轮，每轮现有预算 600 秒，仅预算上限合计就是 210 分钟，尚未含启动/停止。必要的完整验收应集中跑在已通过离线和定向门的同一候选上。

R8 每个阶段只回答一个具体问题：

- A：评价是否可信？
- B：当前图像输入和模型协议能否正确识别？
- C：与当前指令无关的未知物体是否还会拖住整轮，同时该阻断的是否仍阻断？
- 最终验收：同一版能否完整、重复执行？

不要同时试多个提示、阈值和等待时间，再凭总分猜哪个有效。新候选离线门不过就停止升级。若通过，立即推进封包，避免继续加入非必要优化。

## 7. 本版范围及之后的顺序

V0 先覆盖官方线上仿真主流程及横平竖直、位置变化的场景。运行时依据当前图像、深度、指令和实际反馈完成任务，不读取 B03 真值、固定物体清单或位置答案表。当前固定布局类别先验仍是通用性风险，不能把启用它当作 R8 修复；冻结前要明确其在发布配置中的作用，评估场景真值依赖不得混入能力声明。

顺序保持为：**V0 通过与封装 → 用户克隆实例 → 在克隆版重构目录/命名、同步学习文档 → 斜放的 30 场景及更广布局 → 实机标定、感知与控制适配、实机验证。** 不为了先出 V0 删除最终目标；也不在本轮同时实现这些后续范围。

DS 交回 R8 报告须注明：阶段、提交、精确文件清单、已运行/未运行项、原始结果地址、首次失败、是否人工干预。用数据说明结果，不写“审计完整所以类别正确”或“没有报某错误所以已经解决”。
